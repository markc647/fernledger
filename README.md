# Fernledger

**A private, self-hosted tracker for New Zealand bank accounts.** It will sync daily from your bank through [Akahu](https://www.akahu.nz) (until then you import your bank's CSV files), and runs on your own Cloudflare account, on the free plan. One person manages it, and a small group of family members can view it read-only.

> **Status: early development.** The design is settled and the code is being built. Nothing here is ready for real data yet. This README records each decision as it is made, so you can judge whether Fernledger suits you before you use it.

## Who it's for

- **Families overseeing someone else's money.** This is the case Fernledger was built for: an elderly parent's accounts, managed by an attorney under Enduring Power of Attorney, with siblings able to see everything but change nothing. Every change is logged, and printable reports support the attorney's record-keeping.
- **Households** who want one shared, private view of their accounts.
- **Individuals** who want their own finance dashboard without handing bank data to a third-party app.

Fernledger is **one family per deployment**. You run your own copy, nobody else's data is in it, and the project's authors never see yours.

## What it does

- **Daily sync** will bring in transactions from your NZ bank accounts through Akahu, including **pending transactions**, which will be shown as pending until they settle.
- **Imports your bank's CSV exports:** years of history older than Akahu can provide, or as your regular source if you'd rather not use Akahu at all. Fernledger works without Akahu: you import a CSV each month instead of syncing.
- **Bank Time:** a transaction's time of day is shown only when the bank actually supplied one, which is rare, because most banks give a date only. Fernledger never invents a time. Once Akahu Sync ships it will also record when Akahu first saw each transaction, and a transaction's details will show it. A transaction from a bank file has none.
- **Full transaction detail for record-keeping:** open any transaction to see its note and category and everything the bank supplied about it. That way you can show exactly where money went. ASB's CSV export carries none of the payment details but a cheque number, so the counterparty's account number, card suffix, and payment particulars, code and reference will come with Akahu Sync, which is planned.
- **Search and filter:** the Transactions page finds any transaction by text (in the description, the bank's memo, the note, or the payment details the bank gave: cheque number or reference, counterparty account, particulars, code and card), account, category (or Uncategorised), transfers (all, only transfers, or leaving them out) and date range, sorts by date, account, description, category or amount, and pages through years of history. The search is kept in the page's address, so it survives a reload and the Back button. A transaction with a note has a small note button in the list (and on its card on a phone) that opens the note beside it, so the list stays easy to scan; the printed listing keeps each note in full.
- **Your own categories**, from a starter list the Admin can add to, rename and remove. The Admin can override any single transaction's category and add a note, and a list of uncategorised transactions shows what's left. Each category is **Spending**, **Income** or **Loans**, which the Admin sets and which decides how its transactions are added up ([the rules](docs/adr/0012-spending-and-category-kinds.md)): the starter income categories are Income, and a starter Loans category is there for money lent or borrowed (make one for each person, such as Loan – Alice; the [Loans report](#reports) shows what each owes). **Rules** categorise automatically: the Admin sets text to look for in the description or memo, a bank transaction type and an amount range, chooses a category (or marks the transaction as a transfer), puts the rules in order, and sees how many transactions a rule matches before saving it. Rules are used for new transactions as they're imported, and one button, "Apply the Rules to all Transactions", brings the transactions you already have into line with them.
- **Transfers between your own accounts** are detected and left out of spending: money out of one account and the same amount in to another on the same day are paired as a transfer, and the Transactions page says where it went or came from. A payment to an account Fernledger doesn't track still counts as spending. If two unrelated transactions were paired by coincidence, the Admin chooses "Not a Transfer" on either one and both stop being transfers.
- **Monthly budgets** per spending category, set by the Admin from a month of their choice. Unspent amounts don't carry over, and changing a budget doesn't rewrite past months. The Summary's **Budget vs actual** compares this month's budget with what was spent, and the Budgets page shows every spending category's budget and its changes ([how budgets work](#how-it-works)).
- **A Summary for every Member:** the balance of each account, the newest transactions and, last, this month's budget vs actual, as a column of cards on the page Members land on. The balances table has a **Checked** column after the date: "OK" (green) where an account's balance checks agree with the bank, "Check" (red, and by how much) where one disagrees, and a dash where its newest bank balance has not been checked. When Akahu Sync ships and is set up, it will also have a **Sync** column: "Synced" where Akahu reached the account in the last 24 hours, "Not Synced" where not. It will be left out until then, so it never says "Not Synced" of every account. The word and an icon carry the meaning, not the colour alone, and on a phone each account's card has both as labelled rows. There is no card of balance warnings, and nothing about who is signed in (the sidebar's footer says that).
- **A Dashboard for the Admin:** the page the Admin lands on, which is the Summary's column of cards and nothing more: the Admin's pages (import, uncategorised, rules, categories, budgets and settings) are in the sidebar, and the page has no card of shortcuts to them. Each card is a whole row, so the page is one column on a phone and on a wide screen alike. Landing reads only the balances, this month's transactions for budget vs actual and the newest few, never every transaction: the charts, which do, are not on it (below). It is at the Summary's address, and the Admin's navigation calls it the Dashboard.
- **Charts:** net worth over time has a page of its own, **Net worth**, in the sidebar's Reports group, and spending by category is a bar chart on the Spending by Category report, between its total and its table ([how they work](#how-it-works)). Neither is on the Summary or the Dashboard. There is no Charts page: its old address goes to the Net worth page.
- **Printable reports:** the full transaction listing (with each transaction's category and note), each account's balance at the end of every month, what each spending category spent, each month's budgets against what was spent, how much each person owes on a loan, and what came in and was spent in each month, for any date range, laid out for paper. Only the Admin makes them; every Member can open and print the ones the Admin has made, or save them as a PDF from their browser ([how Reports work](#reports)).
- **CSV export** for any date range: the **Export** page, for the Admin and every Member (in the sidebar's Transactions group: under Import for the Admin, after All Transactions for a Member), has the Transactions page's filters (text, account, category, transfers, dates) and a **Download CSV** button that saves the Transactions that match the filters you last searched with, oldest first, to open in a spreadsheet. The Transactions page has no download button, and the Export page has no list.
  - **Columns:** date, account, description, category, note, amount, and everything the bank supplied: its type, memo, reference, counterparty account, particulars, code and card suffix. A bank file has no counterparty account, particulars, code or card, so those columns are empty until Akahu Sync fills them, and the layout stays the same. An amount is dollars as a plain number, with a minus sign for money out, so a spreadsheet can add it up. A transaction with no category says "Uncategorised".
  - **Totals:** Money in, Money out, Net and the number of Transactions come after a blank line, in the second column and not the Amount column, so adding up the Amount column gives the Net. An export of all accounts counts both legs of a transfer between your own accounts in Money in and Money out until transfers ship; the Net is the same.
  - **Formulas are defused with an apostrophe:** a cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return would run as a formula in a spreadsheet, so it gets an apostrophe in front. Amounts are numbers we write ourselves and are never changed.
  - **Opens correctly in Excel:** the file starts with a UTF-8 byte order mark, so macrons (Whāngārei) show properly. A program that reads the file as plain UTF-8 will see an invisible character before the first heading; Python's `utf-8-sig` drops it.
  - **Up to 5,000 Transactions a file** (fewer if Notes are long), because a file stops at about 0.75 MB of text and the free plan gives a request 10 ms of CPU ([ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md)). A file can overshoot that by up to one chunk (about 0.25 MB), so about 1 MB at most. The Export page says how many match before you download, and warns when more match than a file holds, and the file says so when more matched. Export a year at a time to get a longer history. Both limits are estimates from timings, not measurements of CPU: if a request ever fails for CPU, lower the 5,000-row limit, the 0.75 MB limit or both.
- **Change Log** of every edit the Admin makes, visible to everyone: who changed what and when, with the values before and after, newest first. Filter it by type of change and by date.
- **A D1 usage bar for the Admin (optional):** the question the Rules page asks before it applies the Rules to all Transactions (and the progress of a run that is paused for the allowance) can show how much of the free plan's day the Cloudflare account has used, rows read against 5 million and rows written against 100,000, as a bar with a badge and the figures in words, and when the allowance starts again in NZ time. The badge and the colour say how far it has gone, the same way everywhere (the header's bar, below, says the same of the same figures): green **Plenty left**, amber **Running low** from 70% used (30% left), red **Almost used** from 85% used (15% left), and red **Used up** only when the limit has really been reached, not when the percentage rounds to 100. The Admin's header also has one bar, **Free allowance left today**, of whichever of the two has gone further, written as an estimate ("about 62%", since Cloudflare's figures run a few minutes behind), with both figures when you hover over it, focus it with the keyboard or tap it (on a phone it is in the header's menu with the words and the figures written out), and "Allowance unknown" if they cannot be had. Where the header has room (from 86 times the text size) it writes its words and the badge out; in a narrower header it is the bar and its value, with a small shape beside the value when it is going (the words are its name for a screen reader and the first line of its tooltip). It reads the figures as the page loads and every 5 minutes while Fernledger is open in a window you can see, and when you come back to a window whose last reading is 5 minutes old, so about 12 an hour at the most for each open window; never from page to page, and never on a timer of the Worker's. It is for the whole account, so it includes the Members, an Import and the backup, and it runs a few minutes behind. It is off until you add two Worker secrets, `CF_ANALYTICS_TOKEN` (a Cloudflare account API token that can only read Account Analytics) and `CF_ACCOUNT_ID` ([docs/setup.md](docs/setup.md#d1-usage-bar-optional)); without them the page says how to turn it on and nothing else changes. Turning it on lets the Worker ask your own Cloudflare account for its usage, the one extra outbound call ([ADR 0010](docs/adr/0010-outbound-calls.md)), which sends none of your data.
- **Light and dark themes.** A sun or moon button in the header switches between them. A first visit follows your device, and keeps following it as it changes (a device that goes dark at sunset); once you press the button your choice stays, on that device.
- **A header and a sidebar that stay put:** every page has a bar across the top, which stays there as the page scrolls, with the sidebar toggle, where you are (the group and the page) and, on the right, the text size, the theme and Sign out. Beside the page is a sidebar of its pages in groups: the Dashboard (the Summary, for a Member), Transactions, Reports (the Reports page and Net worth, and for the Admin a row for each of the six reports), Set up (the Admin's alone: Accounts, Categories, Rules, Budgets and Settings) and Help. A Member's sidebar has no Set up group, and Accounts is among their Reports instead; Categories and Budgets are not in a Member's sidebar; a Member opens Budgets from the Summary, and both pages stay open to a Member at their own addresses. The sidebar folds to a row of icons with its button or Ctrl+B (Cmd+B on a Mac). Below about 1100px wide it starts that way, so the page is not squeezed, and what you choose is remembered on that device. On a phone it is a menu over the page, and the header's controls fold into one menu, as they do in any window narrower than 56 times the text size (896px at Medium, 1120px at Xtra Large), so that a long page's name is never cut short beside them. The Admin's free allowance bar (below) is in that bar too, as the bar and its value, and needs a little more room, so for the Admin who has turned it on the controls fold into the menu below 66 times the text size (1056px at Medium, 1320px at Xtra Large), and the bar is in the menu then. Neither is printed.
- **Your own title:** for example "Mum's finances", which the Admin sets on the Settings screen. The sidebar shows it at the top (on a phone, in its menu; in the folded sidebar only the logo shows, and the title appears on hover or focus and is what a screen reader calls the link), and so does the top of every report.
- **Add to Home Screen:** opens like an app on an iPad or phone, with its own icon. There's no offline mode and no push notifications. The icon's label comes from a fixed file, so it is normally "Fernledger" whatever title the Admin sets, though some iOS versions use the page title instead. You can rename it when you add it.
- **Sign out:** a "Sign out" link in the header (in its menu on a phone), on every page, ends your Cloudflare Access sign-in, which is what to use on a computer that isn't yours. Cloudflare ends your session for every Access application, not only Fernledger.
- **When your sign-in runs out:** Cloudflare Access ends a sign-in after the session length the Deployer set for it ([docs/setup.md](docs/setup.md#cloudflare-access-one-time-by-hand) suggests 24 hours, so usually every day). If nothing has loaded yet (you opened a tab that had been left overnight), the page says **Your sign-in has expired**, with a **Sign in again** button that loads the same page again, which sends you to Cloudflare's sign-in page and back to where you were. If a page is already open, it stays as it is, with what you had typed in it, and a banner over it says "Your sign-in has expired. Sign in again, then save again; nothing on this page has been lost." Its **Sign in again** opens Cloudflare's sign-in in a new tab, so you can sign in there, come back and press Save again; the banner goes when the next thing Fernledger asks for works. It does not take the keyboard's focus. The Download CSV link checks your sign-in first and saves nothing while it has expired, so Cloudflare's sign-in page is never saved as a file. The page is never kept by the browser, so a tab left open overnight, Reload and Back all reach Cloudflare's sign-in page rather than an app with nothing behind it. **Not signed in** is a different thing: Cloudflare let you through but Fernledger did not accept the sign-in, which signing in again does not fix and the Deployer has to look into (docs/setup.md, Cloudflare Access). Over a page that is open it is a banner too ("Fernledger couldn't confirm who you are. Try again; if it keeps happening, reload the page"), and it goes away when the next thing works; a banner is not printed.

## What it doesn't do

These are deliberate choices. Each is recorded as an [architecture decision](docs/adr/):

- **It can't move money.** Akahu personal apps are read-only, with no payments.
- **No shared hosting.** There's no "Fernledger cloud". You host it yourself (ADR 0006).
- **NZD and NZ banks only.** It's NZ English only, too (ADR 0006).
- **No emails, no analytics, no telemetry.** The app contacts no one but Akahu (only if you use Sync) and your own Cloudflare account: its Access, to check a sign-in, and, only if you add a token for it, its D1 usage figures (ADR 0010). It sends no analytics; the usage figures are Cloudflare's own, read from your own account, and the request carries none of your data. A test fails if any other outbound call appears.
- **No native mobile app.** The web app works in a phone browser.
- **No investment tracking or manually entered assets** in v1.

**Nothing, for a typical household.** Fernledger is designed to run within Cloudflare's **Workers Free plan** (ADR 0004):

| D1 database | 500 MB per database, 100k row writes/day | Years of transactions in a few MB |
| R2 (backups) | 10 GB | Weekly backups of a few MB each |
| Cloudflare Access | Free for up to 50 users | 1–6 people |
| Akahu personal app | Free | One app |

R2 may ask for a payment method on file even within the free allowance (unconfirmed). Fernledger has no paid tier and never will.

## How it works

```
 Your family's browsers
        │  sign in with an email code
        ▼
 Cloudflare Access ── blocks anyone not on your list
        │  signed identity token
        ▼
 Fernledger Worker ── checks the token on every request
        │                  └─ once Sync ships, daily: pulls new transactions from Akahu
        ▼
 D1 database (your account, Oceania) ── weekly backup ──▶ R2 bucket
```

- **Admin and Members.** One Admin, set by email, can edit categories, rules, budgets, overrides and notes. Everyone else is a read-only Member who can view, print and export.
- **Sync** will run once a day, after Akahu's own daily refresh. When Akahu Sync is set up, and only then, a banner will show when data was last synced and turn red after 2 days, for example when a bank connection needs reconnecting. The balances table's Sync column ([What it does](#what-it-does)) is stricter, and for each account: it will say Not Synced as soon as Sync last reached an account more than 24 hours ago, so one missed day shows there before the banner turns red.
- **Import and Sync never overlap.** Each account has a Cutover Date: imported CSV rows cover the period before it, and Akahu will cover it onwards. Nothing is guessed or fuzzy-matched across the two sources (ADR 0003). The Admin sets it in Settings, or takes up the offer of the last date in the file when importing (nothing is set unless the Admin ticks it); an Import then skips rows dated on or after it and says how many. Until accounts can be linked to Akahu, any account can have one; limiting it to linked accounts will ship with that feature.
- **A bad import can be replaced.** On the Import screen, "Replace imported history" removes an account's imported Transactions, never the ones from Sync, and imports the new file in their place, after the Admin confirms and is told how many will go. The Change Log records it. Overrides, Notes and Not a Transfer marks the Admin set on the removed Transactions are carried over to the Transactions that come back with the same number from the bank (ASB makes it from the date and a count for that day). Before the Admin confirms, Fernledger forecasts how many carry over and how many won't. Afterwards the finished screen and the Change Log say how many were carried over, list the first Transactions that lost theirs so they can be set again by hand, and say how many went to a Transaction with a different amount. That last count is the check on the match: if the bank has numbered a day differently since the old export, an Override, Note or Not a Transfer mark can land on a different Transaction. While an Import runs Fernledger holds the Overrides, Notes and Not a Transfer marks of the removed Transactions. If an Import stops part way they stay held: a plain Import of that account gives them to matching Transactions and leaves the rest waiting, and the Import screen says how many are waiting and lets the Admin discard them. Only a replace that completes clears them, and those with no match are then lost. A history of more than 5,000 imported rows is removed in final steps of 5,000, the oldest dates first. A row removed and its replacement imported cost 8 of the free plan's 100,000 database writes a day (the row and its three indexes each way), or 11 if a rule gives the row a category (the rule's result and its entry in the category index are written on import and taken out again on removal). Each override or mark carried over costs up to 8 more and each note 6 more (up to 10 for a transaction with all three of an override, a note and a Not a Transfer mark, because an override and a mark each have an entry in an index of their own, which is taken out again when the old transaction is removed). Each transfer costs more again (4 more to import, because both halves are written, and 3 more to remove, because its own entry in the transfer index goes and its matching transaction is let go). So one day covers about 12,000 rows replaced when few of them have a rule, anything to carry over or are transfers, about 6,500 when every one is a transfer, about 4,700 when every one has a rule's category and an override, a note and a Not a Transfer mark to carry over, and about 3,800 when every one is a transfer with a rule's category and an override and a note to carry over. Beyond that Fernledger stops with "Daily limit reached" and says part of the old history has been removed; choose the same file again the next day to finish.
- **Category precedence:** a hand-set override beats a rule, which beats Akahu's suggestion. A rule never replaces an override.
- **Rules:** the first rule in the Admin's order that matches a transaction wins, and a rule whose category has been removed is skipped. Text matching looks in the description and the bank's memo and ignores capital letters A to Z; a letter with an accent or macron, such as Ā, has to match as typed. A transaction type matches in full (EFTPOS, not part of it). An amount range is on the size of the amount, so $50 covers $50 in and $50 out; the rule can also be limited to money in or money out. Saving, changing, reordering or removing a rule changes no stored transaction by itself: a rule's result is stored with each new transaction as an Import adds it, in the same step, and the Admin applies the rules to the transactions already on file with a button (next item). A rule can mark transfers instead of choosing a category, and applying the rules sets or clears that mark on the transactions already on file too.
- **Applying the rules to everything on file:** the Rules page has one button for it, "Apply the Rules to all Transactions", beside "Add a Rule", which asks first (showing the D1 usage bar, if you have turned it on) and then gives every transaction the result of the rules as they are now: the category of the first rule that matches it, and none for a transaction that no rule matches any more. An override, a note and a Not a Transfer mark are never touched, so a transaction marked Not a Transfer stays out of the transfers even if a rule now marks it as one. The free plan's 10 ms of processing and 50 database queries a request allow only a slice at a time, so Fernledger goes through the transactions in order, a step at a time (up to 1,000, fewer when there are many rules, so that a step reads about 25,000 rows), and keeps its place in the database. While the page is open it asks for the next step as soon as one finishes and shows how far it has got ("Looked at 4,000 of up to 20,000 Transactions (20%)"), about how many steps are left, and a Stop button, in a frame under the buttons; the Change Log records when a run starts, stops and finishes, with the counts. If the page is closed, the two daily crons already there carry the run on slowly (three steps each, one when they are also carrying a backup on), and opening the page again speeds it up from where it stopped. Only one run goes at a time. If a rule is added, changed, moved or removed (or a rule's category is removed) while one runs, it starts again from the first transaction, so that nothing keeps the old rules' result; the rule form says so before you save. Only a transaction whose result changes is written, because writes are the scarcer allowance: 1 write for a transfer mark, 2 for a category (the transaction and its entry in the category index), and the run budgets 3 in case the database bills a category that changes to another as a delete and an insert. A step reads about (the number of rules + 10) rows for each of its transactions. The run keeps to its own share of the free plan's day, 2.5 million rows read and 40,000 written, counted from what the database reports for each step on the plan's day (it changes at 00:00 UTC, around midday NZ time), and pauses until the day changes when the next step would pass it, so the family's use of the app, an Import and the backup keep the rest. 100,000 transactions and 30 rules read about 4 million rows, so that takes two days. The page says when the run is paused and that it carries on by itself after the day changes. If you have turned on the D1 usage bar (see [What it does](#what-it-does)), the question before a run shows how much of the account's day is gone.
- **Transfers:** as an import adds transactions, Fernledger looks in your other accounts for one with the same date and the same amount the other way: money out of one account and the same money in to another. Each pair is a transfer, so moving money between your own accounts isn't counted as spending, and the Transactions page names the other account ("Transfer to Savings") and links to the matching transaction. The Import screen says how many pairs it matched. Only the date and amount decide: the bank's description isn't looked at, and two transactions in the same account never pair. Pairs are one to one, so three identical round-ups out on one day and three in make three transfers, and three out with only two in leave one unpaired until its matching transaction is imported. A payment to an account Fernledger doesn't track has nothing to pair with, so it counts as spending, whatever it's for. A rule that marks transfers makes a transaction a transfer even without a pair: if the banks date the two halves of a transfer on different days, write a rule that marks them as a transfer. If a pairing is wrong, or a rule marks something that isn't a transfer, the Admin chooses "Not a Transfer" on the transaction's page or in its edit panel, after a question that names the matching transaction. Both halves stop being a transfer in one step, and each then counts under its own category's kind (spending when it has none). The mark is on each transaction, not on the pair: Fernledger won't pair either of them with any other transaction either, when a later import brings a new match (Sync will do the same), and a rule that marks transfers stops applying to them, including when the rules are applied to every transaction again. "Undo: treat as a Transfer again" takes the mark off both and pairs each with whatever matches now, the transaction it was marked with first; the Change Log records both. The mark goes with an override or a note when an account's imported history is replaced: it is carried over to the transaction that comes back with the same number from the bank, before the new transactions are paired, and the replace question, the finished screen and the Change Log count it with them. One whose transaction doesn't come back is lost, and the other half keeps its mark. The Admin can also take one half of a transfer out of the transfers by setting a category on it (an override): the override outranks the pairing and the rule, and the transaction then counts under that category's kind (spending, income or loans), but only on that one transaction, and its matching transaction stays a transfer, so "Not a Transfer" is the way to undo a pair. Lending to a child's account is the case for loans: give the half in the lender's account a Loans category (the other half stays a transfer; a Loans category on both halves would cancel the loan out). A transfer shows no category, whatever a rule would have given it. Transfers still count in balances, because the money did move, and the Uncategorised list leaves them out; budgets leave them out of their totals, and reports will too. Replacing an account's imported history lets go of the transfers that history held and pairs the new rows with their matching transactions again.
- **Budgets:** the Admin sets a monthly amount for a spending category on the Budgets page, effective from a month they choose (a year back to two years ahead), and can end it from a month. Income and Loans categories can't have one. The amount for a month is the most recent change on or before it, so setting a new amount from a month never changes the budget of an earlier month. Setting a month that already has an amount replaces it, and setting what a month already has changes nothing. Nothing carries over: what a category doesn't spend one month isn't added to the next, and overspending isn't taken off it. What counts as spending is in [ADR 0012](docs/adr/0012-spending-and-category-kinds.md). The Summary shows this month's spending against each budget, with "Under Budget", "On Budget" or "Over Budget" as an icon and words, and two more rows: "Spending outside Budgets" for the spending categories with no budget, and Uncategorised. Months and dates are New Zealand ones. A budget is more than $0: to have none, end it. Members see budgets read-only, and each change is in the Change Log in plain words. The [Budget vs actual report](#reports) prints every month of a range the same way. The database keeps at most 600 budget changes, for good, counting those kept for categories that are no longer spending or were removed: a month's change can be replaced but not removed, and the Budgets page says how many are used when it gets near. Removing a category takes its budgets out of use in every month, past ones too, and Budget vs actual stops listing it.
- **Charts:** there are two, and each is a picture of figures that are also written out as a table. Nothing moves when a chart is drawn. Net worth over time is on the Net worth page (Reports in the sidebar, for every Member and the Admin), where its table opens itself when you print. Spending by category is on the Spending by Category report, drawn from the report's own figures, so it asks for nothing more. Neither is on the Summary or the Dashboard, so landing there reads only what its three cards show.
  - **Net worth over time** adds up the money in the tracked accounts at the end of each month. It is only the money in those accounts: a loan to or from someone whose account isn't tracked shows as a fall or a rise, and no assets or investments entered by hand are in it. The balances are each account's balance history, the same as the Summary's and the balances report's, picked out at month-ends and carried across quiet months the way the balances report does, never calculated a second time. The Net worth page opens without reading anything, draws it only when you press "Show net worth", and says why it waits. The range (the last 24 months, the last 5 years or all history) is chosen beside the button, before or after: every range reads the same, so choosing first costs one read and not two. The last point is dated the latest date Fernledger holds for any account, not the month's end. Months before an account's first transaction use the balance it had when its transactions begin, so they are an estimate: money that moved into it by then may be counted twice (a transfer from another tracked account in an earlier month, say). After its last transaction an account keeps its last balance, and the chart names the accounts whose transactions stop early and says what the Admin can do. An account with no bank balance to work from yet is left out, and the chart says why in the Summary's words. It draws for up to 49 accounts and says so beyond that, because it takes one database query for each and the free plan allows 50 a request. What it costs, and why a short range costs as much as a long one, is in [ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md). The browser keeps the answer for five minutes while you move around the app, and asks again sooner only after an import or a change of Cutover Date (a reload always asks).
  - **Spending by category** shows what the spending categories spent in the dates you choose for the Spending by Category [report](#reports), as bars between the report's total and its table. The chart is drawn from the report's own answer, so it reads nothing of its own: the report is the one request, and choosing the account and dates is choosing what the chart shows. It uses the same totals as budget vs actual ([the rules](docs/adr/0012-spending-and-category-kinds.md)): transfers between your own accounts, pending transactions, income and loans aren't counted, a refund comes off, and uncategorised counts as spending, so money in that has no category yet comes off it. Categories come biggest first, equal amounts by name, and uncategorised after them. The chart draws the 12 biggest categories that spent something. The report's table lists every spending category that has money in the dates, with the total: one whose money all came back (a full refund) is listed as $0.00 and has no bar, and one with no transactions in the dates is left out. The chart is for the screen: a printout of the report is the table alone, as it always was.

## Reports

A report is laid out for paper, and only the Admin makes one. Each of the six has a page of its own, with a row of its own under Reports in the Admin's sidebar, where the Admin chooses the account and dates and the report appears below the form; the Transactions page also links the Admin to the transaction listing, carrying the account and dates they were looking at, in a new window. Each time the Admin shows a report, its **choices** are kept (which report, its dates, its account, or for loans its category), and the Reports page is a table of them: the report, its dates, its account (or all accounts), when it was last made, newest first. Only the choices are kept, never the figures, so opening a kept report works it out again from today's data. Showing the same report with the same choices again adds no second row; it updates when it was last made. The list holds at most 200, and a new one over that drops the one made longest ago and names it in the Change Log.

Every Member sees the table and can **Open** or **Print** a kept report from its "⋯" menu; Print opens it and starts the browser's print window, which is how a Member saves a PDF on their own computer. A Member's view of a report has no form, and the Worker refuses a Member any report that has not been kept. That stops a Member making a report; it is not secrecy, because a Member can read the same figures on the Transactions page and in its CSV export, in the charts, in the Budgets and in each account's balance history. The Admin can also **Delete** one (it comes off the list, and a Member can no longer open it); **Save** and **Share** are shown, turned off, until they work. A report's address holds what was chosen, so it can be bookmarked or sent on: a Member can open it only if the Admin has kept that report. Print it or save it as a PDF from your browser: a printout is the report alone, without the form. The server stores nothing of a report but its choices.

- **Transaction listing.** Every transaction in the dates you choose, account by account (each with its bank number) and oldest first, with its category, its note and the amount in or out. Under each description is what the bank said about the payment, with what is missing left out: the cheque number or reference, the counterparty's account, the card, the particulars and the code. Each account has its totals, and so do all of them together. It is the record to hand to the family, a lawyer or the court. Every report has the same title block and print layout, described below. A transfer between your own accounts is listed like any other transaction, with "Transfer" where its category would be, and the totals count it: it is money moved, so it is in the money in and money out of the accounts it left and reached, and of all accounts together.
- **Balances over time.** Each account's balance at the end of every month in the dates you choose (account by account, each with its bank number), with its balance when the dates begin and when they end, and the change between them. Daily balances would run to many pages over a few years, so it is one row a month, dated the month's last day. The last row is dated the last of your dates, or the last date Fernledger holds for the account if that comes first (a date is held when the account has a transaction or a bank balance on it), and the report says so rather than show months it knows nothing about. The balances are the account's balance history (worked out from its transactions, starting at the latest bank balance Fernledger can count), picked out at month-ends and never calculated a second time. They are not balances the bank gave for each month-end: a row says "Bank balance" where the bank did give one for that day, and where the two differ it gives the bank's figure and how far the calculated one is from it. Under each account are the [balance check](#correct) differences that fall in the dates, in the same words an Import's result shows, with a note that every balance before a difference's date is worked back from the latest bank balance and so carries it. If there are none, the report says how many balance checks cover the dates and the dates they check together, which can be more than yours, or that none covers them, and never says more than was compared. A balance check that begins on or after your last date is not listed, but a balance its difference moves is still shown beside the bank's figure, and the report says so and does not say the bank agrees. An account with no bank balance Fernledger can count has no balances, and the report says why. The report asks about one account at a time and reads all of that account's transactions each time, however narrow the dates, because a balance is worked out from all of them (ADR 0004).
- **Spending by Category.** What each category spent in the dates you choose, for all accounts or the one you pick, in one table with the total above it. On the screen a [bar chart](#how-it-works) of the biggest categories sits between the total and the table, drawn from the same figures; it is left out of print. The order is the most spent first, equal amounts by name, and Uncategorised after a named category that spent the same, because one function gives the categories, their names, their order and the total ([ADR 0012](docs/adr/0012-spending-and-category-kinds.md)). A category's figure is its money out less any money back, such as a refund, so one that took back more than it paid out says "back", and a "back" amount is taken off the total. Uncategorised counts as spending, so money in that has no category yet comes off it, and it is a row of its own, named as the Summary names it, wherever its amount puts it. Transfers between your own accounts, pending transactions, income and loans aren't counted, and a transaction the Admin marked Not a Transfer counts under its own category's kind. A category with nothing in the dates has no row, and dates with no spending say "Nothing was spent in …" and show no table. The heading of the table on every printed page says what isn't counted, and the Uncategorised row says what it includes, so a page can be read on its own. It is one request however many accounts there are, plus one to check the account you chose. What it costs in database rows, and that its processing time is not measured, is in [ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md).
- **Loans.** How much each person owes, or is owed, on a loan, with the lending and the repayments listed. Each loan is a Loans category, one for each person, named like "Loan – Alice" (that is how the report knows the name to put in "Alice owes"; a category called just "Loans" names no one, and the report says the accounts are owed, or owe, the amount). The Admin gives it the money lent and the repayments with rules or overrides. A transfer to a child's tracked account counts as lending when the Admin gives the half in the lender's account that category with an override (a rule's category does not outrank a transfer), and only that half: the other half stays a transfer, and giving the category to both would cancel the loan out. The report covers the loan you pick, or every loan with a section each (in order of name), from the first transaction up to the date you choose, which starts at today, or from a start date, which begins each section with what was owed before it. With several loans it begins with one line for what each owes and two totals, what the accounts are owed and what they owe, which it never nets against each other; a loan nothing has happened on, such as the starter Loans category before it is used, is named once instead of getting an empty section. A section lists its transactions oldest first, from any account, with the account, the note and the amount, what is owed after each one, and what is owed on the last date: "Alice owes $300.00 to the Accounts" when more money went out than came in, and "Alice is owed $300.00" when more came in. Loans are neither spending nor income, so they are in no budget and in no spending or income figure ([ADR 0012](docs/adr/0012-spending-and-category-kinds.md)); this report is where they are added up. Which transactions are loans is decided once, by the same definition that sets them apart from spending, so the report and the totals cannot differ. It reads a loan 1,000 transactions at a page and stops at 5,000 across the loans, which is lower than the transaction listing's cap because every page of a loan reads the whole loan again (a family's loan is a single request). If a loan has more, the report says so at the top and again before the end, marks the loan it stopped in as partly listed with no amount owed at the end (a figure for only some of the transactions would read as the amount owed) and the loans after it as not listed. What it costs in database rows is in [ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md).
- **Budget vs actual.** Each spending category's budget against what it spent, month by month, for every month the dates you choose touch. A budget is for all accounts together, so this report is too: its form asks for dates only. A budget is for a whole month, so a month is always shown in full: the report covers the whole of every month the dates touch (up to 24 months), its title block gives the dates it covers, and when the dates you chose were part of a month it says which you chose and which it shows. Each month has the budgets added up, what the categories with a budget spent, where that leaves them ("Under Budget", "On Budget" or "Over Budget" with how much is left or over) and the total spending, then a row for each category with a budget that month: the budget, what it spent, and where it stands, in the same words as the Summary's budget vs actual, which a month of the report matches figure for figure. A row says "Budget changed from <month>" in the month its budget changes. Below them are "Spending outside Budgets" (the spending categories with no budget that month, so a category's spending in a month it has no budget is there) and Uncategorised, so every dollar spent is on a row. The budget in a month is the one in effect: the one set from that month or the latest month before it, so a change from a later month never alters an earlier one, and nothing is carried over between months ([how budgets work](#how-it-works)). Categories are taken as they are now, as they are everywhere: a category since made income or loans, or removed, is out of every month shown, past ones too, and a budget kept for it isn't used. When there is more than one month, the report starts with all the months together, which are the months that have ended. The month it is now has had part of its spending set against the whole of its budget, and a month to come has had none, so adding them in would make the categories look further under budget than they are: they are in the report, each on its own and marked, but not in the totals, and the section says which months its figures cover and why. It gives the budgets together against what the categories with a budget spent, and each category's budgets and spending over the months it had a budget with the number of them it was over (the totals add the months up, so one month over budget can hide behind one under it; the count does not). What counts as spending is in [ADR 0012](docs/adr/0012-spending-and-category-kinds.md): transfers between your own accounts, pending transactions, income and loans aren't counted (the heading of every printed table says so, so a loose page can be read on its own), and a refund comes off. When no category has a budget in any of the months, the report says so once at the top. The report is one request for all its months, reading each transaction in them about three times, and the browser adds no amounts ([ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md)).
- **Income vs spending by month.** What came in as income and what was spent in each New Zealand month of the dates you choose, for all accounts or the one you pick, in one table with the totals above it: a row for each month with its income, its spending and the difference, which is income less spending and so is below zero when more was spent than came in. It adds up as the Spending by Category report and its chart do, because one function gives each month's income and spending ([ADR 0012](docs/adr/0012-spending-and-category-kinds.md)). Income is what the income categories brought in, less what went out of them. Spending is money out less money back, such as a refund, so a month that took back more than it paid out says "back". **Uncategorised counts as spending, so money in that has no category yet comes off spending and is not counted as income** (a wage nobody has categorised makes income look smaller and spending smaller by the same amount). When there is any in the dates and the accounts you chose, a notice above the totals and in the heading of every printed page says how much, and to give it an income category to count it; the difference is the same either way. Transfers between your own accounts, pending transactions and loans aren't counted, and a transaction the Admin marked Not a Transfer counts under its own category's kind. A month with nothing in it is a row of zeros, so a quiet month is not mistaken for missing data, and a month whose dates are not over yet, or have not begun, says so on its row. Dates in which nothing was counted at all (nothing, or only transfers and loans) say "There was no income or spending in …" and show no table; a month whose figures net out to nothing, such as $40 spent and refunded in full, has its row. **The dates are counted exactly as you choose them**: when they begin or end part way through a month, that month's row counts only those dates and says which ("Counts only …"), unlike budget vs actual, which always shows whole months because a budget is for a whole month. A report covers at most 120 months (10 years), which the form and the address say rather than open a longer one. It is one request however many accounts there are, plus one to check the account you chose; what it costs in database rows and processing time is in [ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md).
- **Every report says what it is, on every page.** The top of the first page has the app title, the report's name, the account and the dates, and "Generated Thu 8 Oct 2026 at 3:42 pm", when the figures were worked out. A report does not say who made or opened it. Each table's heading repeats those lines at the top of every page it runs onto, in every browser, so a loose page still says what it is and when it was made. The page title is the same words, so "Save as PDF" names the file after them. Text is black on white and at least 12pt, and a row is never split across two pages.
- **Page numbers depend on the browser.** Chrome and Edge (version 131 and later) number each page "Page 2 of 5" in the page margin, using CSS "margin boxes". Firefox and Safari don't draw margin boxes, so they print the report without those numbers. They can number the pages in the browser's own header and footer if that is turned on in the print window, and the report's help sheet (the "?" beside its heading) says so. Everything else on this list is the same in every browser.
- **The Transaction listing lists at most 10,000 transactions.** It reads them 200 at a time, the largest page the Transactions page uses, so no single request is large (ADR 0004), and it stops at 10,000 across all accounts, which is about 27 a day for a year. The Admin, who makes the report, is told so in the help sheet of its page before showing one. If a range has more, the report says so at the top and again before the end, marks the account where it stopped as partly listed and every account after it as not listed (never as having nothing in the dates), and its totals count only what it lists. Choose a shorter range, or one account, to see the rest.

## Security and privacy

We're as clear about the limits as about the protections. The full threat model is in [docs/security.md](docs/security.md).

### What protects your data

- **It lives in your own Cloudflare account.** There's no Fernledger server. The authors can't see your data, lose it, or be breached for it.
- **No passwords in the app.** Sign-in is handled by [Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/policies/access/) with email one-time codes. The app checks Access's signed token (signature, issuer, audience) on **every** request. If configuration is missing, it refuses all requests rather than allowing them (ADR 0002).
- **Only people you list can reach the app at all.** Anyone else stops at Cloudflare's login page.
- **Read-only by default.** Only the Admin can change anything, and every change goes in a Change Log that all Members can see, including the Admin's email address (see [docs/privacy.md](docs/privacy.md#what-a-deployment-holds)).
- **Read-only bank access.** If you use Akahu Sync, its personal-app tokens can't make payments. A leaked token exposes history, not money.
- **Encrypted** in transit (TLS) and at rest (D1, R2). If you use Akahu Sync, its tokens are stored as encrypted Worker secrets, never in code or the database.
- **Protection against cross-site attacks:** changes must come from the app's own address with a JSON body. Strict security headers are set: a Content Security Policy, no framing, no referrer.
- **Safe exports:** CSV cells that would run as spreadsheet formulas, such as a payee named `=HYPERLINK(…)`, are defused with an apostrophe (see CSV export under [What it does](#what-it-does)).
- **Quiet logs:** logs contain only IDs, counts and error types, never transactions, tokens or emails. A test enforces this.
- **Nothing calls home:** no analytics, telemetry, email or third-party scripts.

### If something goes wrong

The breach checklist is in [docs/security.md](docs/security.md#if-something-goes-wrong).

### What it can't protect against

- **Your Cloudflare account is the master key.** Anyone who controls it controls your data. The setup guide requires two-factor authentication on it, and as few account members as possible.
- **Each Member's email is their key.** If someone's inbox is compromised, so is their access, so each Member should protect their email with two-factor authentication.
- **No app-level encryption.** We rely on Cloudflare's encryption at rest. Encrypting inside the app wouldn't add real protection, because the key would live in the same Worker as the data, and it would make search and reports much harder.
- **Cloudflare can technically access data in your account,** as with any cloud host. See Cloudflare's [privacy policy](https://www.cloudflare.com/privacypolicy/).
- **A file you download is on your own.** Once a CSV export is saved, it has no sign-in, can be read by anyone who has it, and isn't in the Change Log. Keep it somewhere private, and delete it when you're done.

### How the code is kept safe

- Open source, so anyone can audit it.
- Every change goes through a pull request with automated checks:
  - type checks and tests
  - [gitleaks](https://github.com/gitleaks/gitleaks) secret scanning, with extra rules that block NZ bank account numbers and bank CSV exports from ever being committed
  - GitHub CodeQL code scanning
- Dependabot keeps dependencies patched, and we use few of them on purpose.
- An independent security audit runs before the first public release, and its findings and fixes will be published.
- To report a vulnerability, see [SECURITY.md](SECURITY.md). Please don't open a public issue.

### Privacy and the law

Read **[docs/privacy.md](docs/privacy.md)** for the details: what the Privacy Act, the PPPR Act and Akahu's terms mean for you, with sources, and the questions to take to a lawyer. In short, and as our understanding rather than legal advice:

- **You're responsible for your deployment, not the project.** Fernledger's maintainers collect nothing.
- **Your own household's finances** are very likely outside most of the Privacy Act (s 27, "personal or domestic affairs").
- **Attorneys sharing a parent's finances with family** are in a grey area. There's no guidance either way, so get advice.
- **Akahu's terms apply regardless:** security, data minimisation, deletion on request, and telling Akahu about breaches.
- **Every Member sees an "About your data" page** saying what's held, who can see it, where it's stored, how long it's kept and who to ask.
- **Nothing is deleted automatically.** Attorneys must keep records of every transaction, and tax rules set minimums, not maximums. You decide when to delete, using the teardown.

### Leaving Fernledger

The teardown (`npm run teardown`) takes a new final backup of everything and downloads it to a folder you choose, then deletes your database. Your data is yours, and you can take it with you or destroy it at any time.

- **The final backup comes first, and is checked.** It is always a new backup, never an older one, and the script checks that every table in the database is in it with the same row count, once after the backup and again right after you confirm, before deleting anything. If it can't be made, downloaded and verified, or the database changed meanwhile, nothing is deleted. Row counts can't see a row edited in place, so don't use the app during teardown. A table the backup can't hold (the manifest lists these) is deleted only if you type its name as well.
- **Deleting needs you to type the database's name.** It is never done on a default answer, and `CI=true` doesn't skip it.
- **You empty the backup bucket yourself, last.** Wrangler can't empty an R2 bucket, so the script deletes the database, then prints how to empty and delete the bucket. Emptying it destroys every backup in it, not only the final one, so download any older backup you want first.
- **If you used Akahu Sync, revoke your Akahu access yourself** (ADR 0008): remove the personal app Fernledger used, or disconnect the bank connections it syncs, in your Akahu account. Deleting the Worker removes Fernledger's copy of the token but doesn't revoke it. With CSV Imports only, there is nothing to revoke.
- **If you made a token for the D1 usage bar, revoke it yourself** in the Cloudflare dashboard (Manage account, Account API tokens). Deleting the Worker removes its copy of the token but doesn't revoke it.
- [docs/setup.md](docs/setup.md#leaving-fernledger-teardown) has the steps, including the few things only you can delete (the Worker and the Access application).

## Where your data is stored

- **The database and backups are created in Oceania by default** (`REGION=oc`). Cloudflare doesn't say which city within Oceania, and has no New Zealand storage region. You can choose another region when you set up (ADR 0007).
- **This is a location *hint*, not a legal residency guarantee.** Cloudflare offers guaranteed jurisdictions only for the EU and FedRAMP.
- **Requests arrive at your nearest Cloudflare location,** such as Auckland. Smart Placement then runs the app next to its database.
- **Read replication is off,** so your data isn't copied to other regions.
- **Region is fixed at creation.** Changing it later means exporting and re-importing.

## Reliability

Fernledger aims to keep your data **correct, current and recoverable**.

### Correct

- **Balance check after every import.** Each bank CSV export states the account's balance at the top. Fernledger compares it with the balance it calculates from its own transactions since the previous export. If they differ, a warning reads, for example, "Balance differs from bank by $5.00 since Wed 30 Sept 2026": the amount, and the date of the previous bank balance it was compared with (that balance may itself have differed). Missing or duplicated transactions can't go unnoticed: the Summary and the Dashboard show the result in the Checked column of the balances table ([What it does](#what-it-does)). The same check will run after every sync, against the balance Akahu reports.
  - The first balance an account has is not checked, because there is nothing to compare it with. The next import is checked against it.
  - A balance dated on or after the account's Cutover Date is not checked, because those days are meant to come from sync. Neither is a balance in a file that ends before that balance's date.
  - A transaction the bank adds late to the last day of an earlier export doesn't raise a false alarm. Pending transactions are never counted.
  - A transaction backfilled with the same date as an older balance (from a file that was missing it) isn't counted by that balance until that date's file is imported again.
  - If the Admin ticks "set the Cutover Date to the last date in this file" when importing (it is offered, never set unless ticked), the file's own balance is dated on or after that Cutover Date and isn't checked. Choose a later Cutover Date, or import a file that runs past it, for that balance to be checked.
  - "Since" is the date of the earlier balance the difference was checked against, not the date it was first seen ([ADR 0011](docs/adr/0011-balance-check-since-date.md)).
- **Syncs will be safe to repeat.** Transactions will be matched by Akahu's ID. Each sync will also re-check the last 30 days, because banks sometimes delete and re-issue a transaction.
- **Transactions are never deleted because a bank link changed.** If your bank reconnects or changes systems and Akahu issues a new account ID, Fernledger will flag "Account link broken". The Admin will re-link it in one step.

### Current

- **Sync will run daily, with an automatic retry** a few hours later if it failed. A sync will only count as successful when every account has finished.
- **The status banner will say what's wrong and what to do.** For example: "ASB needs reconnecting in Akahu (Admin)", "Akahu unavailable — retrying" or "Akahu token invalid (Admin)". Members will see the status, and the Admin will see the action. It will be shown only when Akahu Sync is set up, and will turn red after 2 days without a successful sync.

### Recoverable

- **Weekly full backups** go to your own R2 bucket and are all kept. They're a few MB each, so years of them fit in the free allowance. Each backup includes a manifest of row counts and checksums.
- **Point-in-time restore:** Cloudflare D1 can restore your database to any point in the last **7 days** on the free plan, or 30 days on paid plans.
- **Restore is tested:** CI tests the restore script, and you should do a restore practice run twice a year ([docs/setup.md](docs/setup.md#restore-practice-run-twice-a-year)).
- **Safe upgrades:** before a release changes the database, the deploy script takes a complete backup, then records a restore point. If the backup fails, it stops before changing anything. If an upgrade goes wrong, roll back by redeploying the previous release, and restore the restore point only if the data needs it ([docs/setup.md](docs/setup.md#rolling-back)).

### If the Admin becomes unavailable

The Admin also owns the Akahu connection. If they can't continue, viewing and backups keep working, but edits and syncing stop. The docs include a **succession procedure**: who else should hold access to the Cloudflare account, how to change the Admin, and how a new Admin connects their own Akahu app. If you act under Power of Attorney, plan this early.

### What we don't promise

- **No failover.** If Cloudflare or Akahu has an outage, Fernledger is unavailable or out of date until it ends.
- **Nothing is lost during an outage.** Your bank remains the source of truth, and the next sync catches up.

## Accessibility

Fernledger is often used by families where some members are older, and by people managing their own money in later life. It's built to be easy to read and use.

- **Standard:** every release meets [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/). Automated accessibility checks (axe) run on every page in CI, and colour contrast is checked in both the light and the dark theme, on every page and what opens over it. Before each release we test by keyboard only, with a screen reader (VoiceOver/NVDA), and at 200% zoom.
- **Readable text:** a text-size control in the header (**Small / Medium / Large / Xtra Large**: 14px, 16px, 18px and 20px) is remembered on each device. **The default is Medium, 16px.** **Small (14px) is a choice someone makes, never what they start with**, and it makes everything 12.5% smaller, tables included. **All text that is not a heading is exactly the size chosen**, in every part of the page: the sidebar and its sub-menus, the breadcrumb, buttons, tables, cards, form fields, menus, tooltips, captions and hints. Headings are larger than that and grow with it. Everything works at 200% browser zoom with no sideways scrolling.
- **Plain language:** "Money in" and "Money out", not debit and credit, where a total or a Rule says which way money went; a Transaction's amount is its signed figure alone ("+$1,234.56", "−$1,234.56"), with no words under it, on screen or on paper. Dates like "Thu 8 Oct 2026". A date box is wide enough for the longest date ("Wed 20 Sept 2000") on one line at every text size, and boxes that don't fit side by side stack on a narrow screen rather than split a date over two lines. Technical settings, such as cutover dates and account links, appear only in the Admin's settings, each with a one-line explanation.
- **The current page is never shown by colour alone.** In the sidebar it has a heavier font, a filled row and a bar at the start of the row that is 3:1 against the sidebar in both themes, and the link says it is the current page to a screen reader; in high contrast it takes your palette's highlight.
- **Colour is never the only signal.** Amounts carry a sign, and statuses carry an icon and words. Red and green are chosen to stay distinguishable for colour-blind users. Contrast meets AA in both light and dark themes.
- **Respects your device:** follows your light/dark setting (until you use the theme button), reduced-motion preference and Windows high-contrast mode. In high contrast the current page, the chosen text size and the control that has focus are all drawn in your palette's highlight and an outline, not in a fill or shadow that high contrast removes.
- **A calm home page for Members:** read-only Members land on a simple Summary. It shows each account's balance (with whether it agrees with the bank), this month's spending against budget and recent transactions; when the data was last updated will join them. They are cards, one under the next, and nothing on it reads every transaction; the filters are one click away. The two charts have pages of their own (Net worth, and the Spending by Category report). A chart is a picture of figures that are also written out in a table, so a screen reader and a printout have them, and it is drawn at once rather than moving. Its colours keep 3:1 against the page in both themes, and in Windows high-contrast mode it is drawn in your text colour.
- **Anything that can be dragged can be done another way.** The Admin can put the Rules in order by dragging a Rule by its handle (with a mouse, a finger or the keyboard: Space or Enter to pick it up, the arrow keys, Space or Enter to drop it), and every Rule's Actions menu has Move up and Move down, which is what WCAG 2.2's rule on dragging asks for. A row's changes are a button named for the change when there is only one (Edit a Transaction, Rename an Account, Edit a Budget), whose form opens as a panel directly under that row with the page left where it was, and a menu on its "⋯" button when there are two or more (the Rules, the Categories, the kept Reports); either is 44px, and a form or a question that one opens takes focus and gives it back to its button when it is closed (on the Uncategorised page, where saving takes the Transaction out of the list, to the "Saved …" line that takes its row's place, not to the next Transaction). What was typed in a panel and not saved is kept until it is saved or cancelled, even if another row's panel is opened or the table becomes cards.
- **Explanations are out of the way.** What a page is for, how a form is filled in and how a figure is worked out are in a sheet that opens from a "?" beside the page's heading, so a table or a form is not pushed down the page by words you have read once. It slides in from the right, ends with a Close button, closes with Esc, and gives focus back to the "?". It is the same at every text size. A report's own notes about its figures (what is counted, how a figure is worked out) are in the same kind of sheet, behind a "?" beside the report's own title, and a printed report keeps them as a section before the figures. Warnings, errors and the figures stay on the page, and so do short hints for a field: under it or, on the Rules form, behind a small "?" beside its name (a screen reader reads the hint with the field either way), and so does the Export page's explanation of what Download CSV saves and what a saved file leaves unprotected, because it is needed each time a file is saved.
- **Phones and tablets:** large touch targets (at least 44px; the days of a calendar are 44px, and shrink to about 39px on a 320px-wide screen so that seven fit), and tables become cards on narrow screens. Tested on iPad Safari and Android. There are two exceptions, both over WCAG 2.2's minimum of 24px:
  - **With a mouse, the sidebar's rows and the header's buttons are 32px tall.** That is the compact look they are designed in; on a touch screen (any device whose main pointer is a finger) the same rows and buttons, and the icons of the collapsed sidebar, are at least 44px. A laptop with a touch screen and a mouse gets the compact size.
  - **At the Small text size every target is 12.5% smaller**, because everything is sized in rem: a 44px target is about 38px and a 32px one 28px. Small is a choice, and is not the size anyone starts with (Readable text, above).
- **Printed reports for any reader:** at least 12pt text, black on white, page numbers ("Page 2 of 5"), table headings repeated on every page, and a header showing the account, date range and when the report was generated. Page numbers ("Page 2 of 5") are printed by Chrome and Edge 131 and later; other browsers number pages only in their own header and footer, if that is turned on (see [Reports](#reports)).
- **Help signing in:** a one-page printable "How to sign in" guide for family members.

## Getting your history in

Akahu's history is limited:

| | History available when you first connect |
|---|---|
| Akahu personal apps | Up to 2 years |
| ASB | About 12 months |
| Kiwibank credit cards | About 180 days |
| SBS | About 6 months |

For anything older, export CSVs from your internet banking and **import** them. Fernledger parses the file in your browser and uploads it in chunks, so even 7 years of history stays within the free plan. **ASB CSV** is supported first. Other banks' formats will follow, and contributions are welcome.

## Setting it up

*The full guide arrives with the first release.* In outline:

1. **Before you start:** create an Akahu personal app and note its two tokens. Create a new Cloudflare account and turn on two-factor authentication.
2. **Deploy:** run `npm run setup`, which creates the database and backup bucket in your chosen region, then `npm run deploy`. Both ask you to confirm the Cloudflare account first, and take `--yes` to skip that prompt when there is no terminal. [docs/setup.md](docs/setup.md) has the steps. Or use the **Deploy to Cloudflare** button (coming before the public release).
3. **Lock it down:** turn on Cloudflare Access for the Worker, add your Members' emails, and paste the two Access values into the app's secrets. Until you do, the app refuses every request.
4. **Load your data:** import your CSV history, link each account to Akahu, and let the first sync run.
5. **Optional, to see your database usage:** add the two secrets for the D1 usage bar ([docs/setup.md](docs/setup.md#d1-usage-bar-optional)). The free plan's daily limit on rows read is easy to reach while you are setting up Rules.

**Choosing public names:** your app's address (`fernledger.<subdomain>.workers.dev`) and sign-in page (`<team>.cloudflareaccess.com`) are visible to anyone who sees the link. Use neutral names, not the account holder's name.

## Updating

**How you hear about updates:**
- If you used the Deploy button (still Planned, see Status), a small GitHub Action in your copy checks weekly for a new Fernledger release. When it finds one, it opens a pull request with the release notes. Review it and click **Merge**, then run `npm run deploy` from the merged commit: that is the step that takes the pre-deploy backup, records the restore point and applies database migrations. If your Cloudflare build already deploys on merge, it skips those, so run `npm run deploy` as well (or instead). The action needs one setting turned on in your copy ([docs/setup.md](docs/setup.md#update-pull-requests)).
- **You are trusting upstream.** A merged update runs upstream's code in your build and deploy (package scripts, `.githooks`, `scripts/`), so read the pull request as you would any dependency update. The setting above lets Actions approve pull requests as well as create them, and pull requests opened with `GITHUB_TOKEN` don't trigger `pull_request` checks, so no CI runs on them.
- You can also **Watch → Releases** on this repo, and subscribe to its security advisories.
- The app itself never checks for updates. That would mean contacting GitHub, and Fernledger contacts no one but Akahu (only if you use Sync) and your own Cloudflare account: its Access, to check a sign-in, and, only if you add a token for it, its D1 usage figures (ADR 0010).

How releases are made and tested is in [docs/releasing.md](docs/releasing.md).

**Command-line deployments:** check out the new release tag, then run `npm run deploy`. It needs `npm run setup` to have been run once for this Cloudflare account. Add `--yes` to skip the confirmation prompt when there is no terminal ([docs/setup.md](docs/setup.md)).

**What version numbers mean** ([semver](https://semver.org)):

| Release | Example | What to expect |
|---|---|---|
| Patch | 1.2.**3** | Fixes only, and an add-only migration if the fix needs one. Security fixes ship this way immediately, with a GitHub Security Advisory |
| Minor | 1.**3**.0 | New features, no manual steps |
| Major | **2**.0.0 | Manual steps, explained in the upgrade notes |

Only the latest release receives fixes. Please stay current.

**Your data during an upgrade:**
- Before any database change, the deploy script takes a complete backup and records a restore point. If the backup fails, nothing changes.
- Database changes only ever **add** at first. Anything is removed only in a later release, once nothing uses it, so **rolling back to the previous version always works** (ADR 0009).
- You can skip versions: CI upgrades a sample database from each earlier minor release to the latest and checks the data is intact ([docs/releasing.md](docs/releasing.md#sample-databases)). No minor release has shipped yet, so the one sample is a placeholder that is replaced when v0.1.0 is released.
- Large data changes run in chunks and resume where they left off, so they stay within the free plan's daily limits.
- If a release needs a new setting, the Settings screen shows the Admin **"Setup needed"** and switches off just that feature until it's done. A feature you don't use, such as Akahu Sync, can stay off. Everything else keeps working.

## Technology choices

| Area | Choice | Why |
|---|---|---|
| Hosting | Cloudflare Workers + D1 + R2 | Free plan, no servers to run, built-in sign-in (ADR 0001, 0004) |
| Sign-in | Cloudflare Access | No passwords in the app (ADR 0002) |
| Database access | Plain SQL, no ORM | The app is mostly reports, which are best written as SQL (ADR 0005) |
| API | [Hono](https://hono.dev) + [zod](https://zod.dev) | Small, Workers-native, typed, validates input at the boundary |
| UI | React, [shadcn/ui](https://ui.shadcn.com), Tailwind | Clean neutral look, light/dark, accessible components |
| App shell | shadcn's [Sidebar](https://ui.shadcn.com/docs/components/sidebar) (the sidebar-16 layout), with the Radix [Dialog](https://www.radix-ui.com/primitives/docs/components/dialog) (the phone's sheet), [Tooltip](https://www.radix-ui.com/primitives/docs/components/tooltip) (the names of the collapsed sidebar's icons) and [Slot](https://www.radix-ui.com/primitives/docs/utilities/slot) | A header and sidebar on every page, built on accessible parts; each Radix package on its own, not the whole `radix-ui`, to keep what a page downloads small |
| Icons | [lucide-react](https://lucide.dev) | The sidebar's and header's icons, as the shadcn components use; each is imported by name, so only the ones used are shipped |
| Tables | [TanStack Table](https://tanstack.com/table) | Sorting, filtering and paging for transaction lists |
| Table look, row actions and order | shadcn's [Table](https://ui.shadcn.com/docs/components/table) and [Dropdown Menu](https://ui.shadcn.com/docs/components/dropdown-menu) (the Radix package on its own), and [dnd-kit](https://dndkit.com) | One look for every table (a shaded heading row, a divider between rows, a rounded box; a printed report keeps its plain paper layout), a button named for the change on each row the Admin can change in one way (the Transactions, Accounts and Budgets), opening its form as a panel under the row, a "⋯" menu on each row with two or more (the Rules, Categories and the kept Reports), and dragging the Rules into order, with a mouse, a finger, the keyboard and a screen reader; dnd-kit is loaded only by the Rules page |
| Charts | [Recharts](https://recharts.org) via shadcn Charts | Matches the UI theme |
| Dates | [react-day-picker](https://daypicker.dev) via shadcn Calendar, with [Radix Popover](https://www.radix-ui.com/primitives/docs/components/popover) | A calendar to choose a date from, with the keyboard, a screen reader and a phone; loaded when one is first opened |
| Routing/data | TanStack Router + Query | Typed routes, caching |
| Tests | Vitest + Cloudflare's Workers test pool | Business logic and SQL tested against a real local D1 |
| Browser tests | [Playwright](https://playwright.dev) | Accessibility (axe), print layouts, and phone/tablet layouts in a real browser |
| Accessibility checks | [axe-core](https://github.com/dequelabs/axe-core) in CI | WCAG 2.2 AA on every page; colour contrast in both themes |
| Deploy | Wrangler | Standard Cloudflare tooling |

**Conventions:**
- Money is stored as integer cents, and dates are NZ dates.
- Business logic lives in pure, tested functions.
- Amounts are right-aligned in fixed-width digits, and always shown with a sign as well as a colour, so they read correctly for colour-blind users and on paper.

Why not build on Actual Budget, Sure or Firefly III? Each was evaluated in [ADR 0001](docs/adr/0001-custom-build-on-workers-d1.md).
