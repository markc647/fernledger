# Coding standards

Reviewers apply these to every diff. They're judgement calls. Anything mechanical is enforced by `npm run check` and CI, not listed here.

## Domain language
- Code, tests, docs and messages use `GLOSSARY.md` terms, not its _Avoid_ synonyms ("Member", not "user").
- Fields that come straight from a bank or Akahu are prefixed so they can't be mistaken for a glossary concept (`bankMemo`, not `memo`, which would read as a Note).

## ADR conformance
- A diff that contradicts an ADR in `docs/adr/` says so explicitly in its PR or commit message.
- These ADRs are the ones most often broken in passing:
  - **0004, free plan:** each invocation gets 10 ms of CPU and 50 subrequests / D1 queries. Loops over Transactions run as SQL or in chunks, and writes are batched.
  - **0005, plain D1 SQL:** no ORM or query builder.
  - **0007, data location:** Oceania is a location hint, never "stored in Sydney" or a residency guarantee.
  - **0008, Akahu optional:** anything about Akahu (tokens, revoking, Sync) is conditional on using Akahu Sync.
  - **0009, add-only migrations.**

## Structure
- Business logic lives in pure functions with their own tests. Worker handlers stay thin: authenticate, validate, call the logic, respond.
- Every `/api` request is authenticated via the Access JWT and fails closed.
- Only the Admin makes a Report. Every route under `/api/reports` sits behind `requireKept` (`worker/kept-reports.ts`): the Admin reads any Report, which is how one is made, and a Member only one the Admin has kept, and a path it does not know is refused too. What is kept is a Report's choices, never its figures (opening one works it out again), and it is written by `POST /api/kept-reports` when the Report page shows one (`ReportFrame`): a Member's view is never a showing. A Worker test of a Report's figures reads as the Admin, and calls `keepReport` (`worker/test-support.ts`) where it shows that a Member reads the same. A browser spec that shows a Report as the Admin calls `forgetKeptReportsAfterEach()` (`e2e/report-helpers.ts`), because the list is shared by every spec and both themes, and opens one as a Member with `signInToOpen`.
- A Transfer is never spending or income. A query that lists, filters or totals spending (Budgets, Reports, the Summary, a Category total) builds from `effectiveCategory()` in `worker/effective-category.ts` and uses its `isTransfer`, never its own version of "paired, or a Rule marks it, unless the Admin said Not a Transfer", and a test proves a Transfer is left out. Spending and Income, by Category or month, come only from `buildSpending` and `rollUp` (by Category) and `buildMonthlySpending` and `rollUpMonthly` (by month), all in `worker/spending.ts` ([ADR 0012](docs/adr/0012-spending-and-category-kinds.md)); don't total them again somewhere else. Who can say Not a Transfer comes from `markable` in `effective-category.ts` and reaches the pages as `canMarkNotTransfer`; the pages decide nothing from a pairing or a Rule.
- A Category shown to a reader (a page, a Report, a CSV file) comes from `effectiveCategory().shown`, never its `id`, `name` or `source`: a Transfer has none, and shows as a Transfer rather than as Uncategorised or under a Rule's Category.
- A batch that adds Transactions (Import today, Sync when it lands) puts `pairTransfersStatement` (`worker/transfers.ts`) in the same batch, after the insert and the Rules, so a Transfer is never missed. A batch that removes Transactions also lets go of their matching Transactions in the same batch, because a pair's pointer is deliberately not a foreign key (`migrations/1501_transfers.sql`).
- Every Admin change is written with `recordChange` (`worker/changelog.ts`), which batches it with its Change Log entry. Never write to the Change Log separately; a change that makes a second entry (a kept Report that drops another) puts `changeLogStatement`'s statement after the one it describes, in the same batch. Each entry has a `type` from `CHANGE_TYPES`; a new kind of Admin change adds its type there so Members can filter by it.
- A change that reads and then writes (a rename, a Setting, a Budget, a Rule) is not alone: another request can land between the two. Pass the read into the write's `WHERE`, set `onlyIfChanged` with that statement last in the batch, and when nothing changed re-read and answer 404 (it is gone), 200 (it is already as asked) or `CHANGED_MEANWHILE` (`worker/validate.ts`; it is something else now). Its test interrupts the request with `callWhileInterrupted` (`worker/test-support.ts`) and fails with each guard made always true, one at a time.
- Log with `logEvent` (`worker/log.ts`), not `console`: it takes only an event name, an ID, a count and an error, which it reduces to its class.
- A feature that needs optional configuration declares it in `worker/features.ts` and puts `requireFeature` in front of its routes, so it shows "Setup needed" rather than failing. Messages come from the declaration, never from a missing or present value.
- Change requests need the Admin, a same-origin `Origin` and a JSON body; the guard runs before any handler, so handlers don't re-check. It checks the JSON content type only; each handler validates the body's shape with zod. The exceptions are the row lists: Import rows and carry-preview rows (`worker/import-rows.ts`, `badRowField` and `badPreviewField`). 500 rows through a zod schema cost more than the 10 ms CPU budget (ADR 0004), so they are checked by hand and the request envelope around them still uses `zod/mini`. Don't hand-validate anything small.

## Migrations
- Files in `migrations/` are named `<ticket number × 100 + n>_<name>.sql`, n from 01 to 99, lower-case name. Ticket 8 owns `0801_…` to `0899_…`; ticket 2 owns `0201_…` to `0299_…`. Parallel tickets can't collide, and wrangler applies files in numeric order. A UI ticket has no issue number, so it takes `9N01_…` to `9N99_…` for its number N (U6 owns `9601_…` to `9699_…`).
- Add a new file rather than editing one that has merged. Migrations are add-only (ADR 0009): new tables, nullable columns (or NOT NULL with a constant default, ADR 0009), indexes. `DROP` and `RENAME` wait for a later release.
- `npm run migrations:check`, part of `npm run check`, fails on a duplicate prefix, a badly named file, or any `DROP` or `RENAME`.
- `npm run check` also upgrades every sample database in `test/sample-dbs/` and fails if data is lost or a merged migration was edited ([docs/releasing.md](docs/releasing.md#sample-databases)). A migration that rewrites existing values needs its expected change written into that test.

## Outbound calls
- The app contacts no one but Akahu (only if you use Sync) and your own Cloudflare account: its Access, to check a sign-in, and, only if you add a token for it, its D1 usage figures ([ADR 0010](docs/adr/0010-outbound-calls.md)). Don't add a `fetch`, socket or beacon without Akahu Sync's reason for it or the D1 usage bar's: `worker/outbound.test.ts` and `scripts/outbound-calls.test.mjs` fail on one, and a new call extends both (a file in the second's `ALLOWED_FILES` with its one address, and a run of the first that sees exactly that) rather than widening what they allow.

## Docs
- Each meaning has one home. `README.md` carries every decision for prospective users. Other docs link to README sections rather than restating them, and add only detail the README lacks.
- Describe what exists in the present tense and what's coming in the future tense ("will ship"). Never promise a process that doesn't exist yet.

## Security and privacy
- Every trust boundary has negative tests, not just the happy path: a wrong issuer, an expired token, a spoofed `Host`, a Member attempting a write, a missing setting (fail closed).
- Error messages and logs identify a problem by line number, field name, ID, count or error class. They never echo a transaction value, email or token.
- Workers invocation logs stay off in `wrangler.jsonc` (`observability.logs.invocation_logs: false`): they record request URLs and headers, including the Access email. A script test fails if it's re-enabled.
- Secret-scan allowlists match specific fake values (bank code 99), never whole paths or whole rules.

## Tests
- Test behaviour at three seams: the Worker boundary, the bank CSV adapters, and the browser (Playwright, kept small). Worker tests go through the real request path (`exports.default.fetch`). Call `worker.fetch` directly only when the test must change the Worker's env.
- Fixtures are made up and follow the hard rule in `AGENTS.md`. See `docs/bank-formats/` for each layout.
- A browser spec that creates Accounts takes numbers no other spec uses (the specs and both themes share one database), from the registry in `e2e/account-numbers.json`; `npm run test:scripts` fails on a clash.
- A browser test runs in the light project. The dark project runs only the tests tagged `@theme` (`test('…', { tag: '@theme' }, …)`, or on a `test.describe`), so tag one only when its result can differ by theme: it measures a colour or a contrast, looks at how something is drawn (a fill, an outline, focus, a chart's colours), runs in forced colours (Windows high contrast), checks print from the dark theme, or tests the theme toggle. A test of behaviour, text, layout or an axe scan is not tagged. A test that sets `colorScheme` itself needs no tag.
- A per-page axe scan (`noAxeViolations`) leaves `color-contrast` out; every other rule still runs. Contrast is measured once, in both themes: the theme's own pairs by `scripts/theme-contrast.test.mjs`, and text on a tint or a translucent fill as it is painted by the sweep in `e2e/contrast.spec.ts` (`@theme`). A new page, or a new coloured state (a status, a notice, a badge), is added to the sweep and not scanned with `{ contrast: true }` in its own spec.
- A test proves something only if it would fail when the code it protects is removed. Reviewers check this for security tests.

## Dependencies
- Add one only when a few lines can't do the job. Prefer the smallest entry point (`zod/mini`, not `zod`).

## UI
- shadcn/ui components and plain NZ English ("Money in" / "Money out"). The commitments (WCAG 2.2 AA, text sizes, touch targets, zoom, colour, high contrast) are in README [Accessibility](README.md#accessibility); a diff that breaks one fails review.
- Use the shared building blocks rather than formatting by hand: `formatAmount`, `formatBalance`, `formatDate` and `formatInstantDate` (`src/lib/format.ts`), `Amount`, `Status`, and `ResponsiveTable`. `/styleguide` shows them, and the browser tests scan it.
- Every table on screen is a `ResponsiveTable`, which has one look (shadcn's Table: a muted heading row, a divider between rows, a row that lights as it is pointed at, in a rounded box, with the same cards on a phone). Never write a `<table>` of your own or style one apart: a change to the look is made once, in `src/components/responsive-table.tsx`. A table in a card (the Summary, the Dashboard, a Change Log entry) is `look="in-card"`, without a second border; on paper the look gives way to the paper layout (`print:` there). A page's spec calls `expectTableLook` on its table (`e2e/table-look-helpers.ts`).
- A row of a table that the Admin changes has its actions in a "⋯" menu, `RowActions` (`src/components/row-actions.tsx`), named for its row ("Actions for Rule 3"), with a `RowAction` for each and the destructive one last after a separator: never a button on the row. The Member's table has no Actions column. An action runs once the menu has closed, so that a form or a question it opens can take focus (an open menu holds it); the page puts focus back on the row's button, which has an `id` of its own, when that is closed without a change. Never put the action itself on `onSelect` of a `DropdownMenuItem`.
- Whatever can be done by dragging can be done without it (WCAG 2.5.7): rows that are dragged into order are `SortableRow`s in a `SortableFrame` (`src/components/sortable-rows.tsx`, the only place dnd-kit is imported, so only a page that drags loads it), with a handle column (`handle: true`) that has an accessible name for its row, and the menu has Move up and Move down. A move is shown at once and saved with the whole new order; if it is refused or fails, the order before comes back and the page says so. What a screen reader is told is in the page's words (`dragAnnouncements`, `src/lib/rules.ts`), with the Glossary's names.
- A date a form takes is a `DatePicker` (`src/components/date-picker.tsx`), not `<input type="date">`. A `Date` that came from the calendar is in the device's local time, so it is never read or written through UTC (`new Date("2026-10-08")`, `toISOString()`), which moves the day for anyone east or west of it: go between it and `YYYY-MM-DD` with `dayOf` and `isoDateOf` (`src/lib/calendar-day.ts`; `scripts/calendar-day.test.mjs` runs them in other time zones). A browser spec chooses a date with `pickDate` (`e2e/date-helpers.ts`). A `DatePicker` is never narrower than its longest date (`--date-field-min` in `src/index.css`) and never wraps it, so a row of them is a `date-fields` grid or a `flex-wrap` row that starts a new line when it is short of room, and none of their wrappers is `min-w-0`.
- All text that is not a heading is the size the text size control chose, so give it none: `text-base` is that size, and `text-xs` and `text-sm` are too (`src/index.css`, which is how stock shadcn components stay stock). A fixed size (an arbitrary length such as `text-[…]` with px or rem in it, or `fontSize`) fails `scripts/one-text-size.test.mjs`, and so does text in another size in `e2e/display.spec.ts` ("one size for all text"). A heading is `text-lg`, `text-xl` or `text-2xl`, larger than the text at every size; a printed Report has its sizes in pt (`print:text-[12pt]`). Use `size="touch"` for interactive targets. A control in the header or the sidebar takes its size from `Button` (`compact`, `icon`) or `SidebarMenuButton`, which are README [Accessibility](README.md#accessibility)'s sizes.
- A page is added to the sidebar by `staticData: { nav: { label, group, order } }` in its route file (`src/lib/nav.ts`); a new group is added to `NAV_GROUPS` there and given an icon in `src/components/app-sidebar.tsx`. Nothing in the shell lists pages. A page that belongs to another has no row of its own: it declares `nav: { label, parent }` (the parent's address), the breadcrumb names it under its parent's group, which is a link to the parent (the way back on a phone), and the sidebar marks the parent. A page with a row of its own that is also a part of another declares `within` for the same link and keeps its row marked; `member: { parent }` makes it a page of the other for a Member, who has no row for it. That is how the six Reports are declared, by `reportNav` (`src/lib/report-nav.ts`): a row each for the Admin, who makes them, and for a Member pages of Reports. A page that is its own row in a group, though its address begins with another row's (Net worth, `/reports/net-worth`, beside Reports, `/reports`), declares `group` and `order` and no `within` or `parent`: the page whose address is longest is the one that is marked.
- Add a new page to the zoom test in `e2e/display.spec.ts`.
- Text a reader reads once (what a page is for, how a form is filled in, how a figure is worked out, what a Report holds) goes in the page's help sheet, not under its heading, where it pushes the table or form down. A page's heading is `PageHeading` with `help` (`src/components/help-sheet.tsx`): a "?" button, "About this page", on the same row as the h1 (a touch target, 44px like every button), which opens `HelpSheet` from the right with Close at its foot (never the speech-bubble icon, which is a Transaction's Note). What stays on the page is what the reader needs each time: a warning about the figures (it prints, and the sheet does not: Net worth's `NET_WORTH_ESTIMATE`), an error, a short hint for a field (`aria-describedby`), the figures and the data, and the Export page's explanation of what Download CSV saves and what a saved file leaves unprotected (README [Accessibility](README.md#accessibility)), which has no "?". A page with several things to explain gives each a `HelpHeading` (the Summary's cards, the Rules page's Apply box, the Settings' Cutover Dates). A Report's help is its `about` and `note` in `REPORTS` and `PRINT_HELP` (`src/lib/reports.ts`), written once, which `ReportGate` puts in the sheet (the `note`, which is about the Admin's form, only for the Admin); the printed Report keeps its own "About these figures". A new page with such text is added to the list in `e2e/help-sheet.spec.ts`, and a spec that looks for the text opens the sheet first (`openHelp`, `e2e/help-helpers.ts`).
- The Summary and the Dashboard are one column of cards, `SummaryCards` (`src/components/summary/summary-cards.tsx`): a new part of either is a `DashboardCard` (`src/components/summary/dashboard-card.tsx`: a region named by its `h2`), a whole row, added there in the order it is read (Balances, Budget vs actual, the newest Transactions), so the two pages cannot differ: they add only their heading (with its "?", whose sheet is `SummaryHelp`: a card keeps its table and not its explanation), with no card of the Admin's shortcuts (the sidebar has those pages) and no line saying who is signed in (the sidebar's footer does). Balances has a Checked and a Sync column, which README [What it does](README.md#what-it-does) says the words of; Sync is there only when `featuresQuery` says Akahu Sync is set up (ADR 0008), and is left out, not shown empty, when it is not or cannot be read. Nothing on the landing page reads more than a month of Transactions: a card that does has a page of its own and waits for a button, as the Net worth page's chart does ([ADR 0004](docs/adr/0004-runs-on-workers-free-plan.md)). `ui/card.tsx` stays stock shadcn: what a card needs on top (a border that survives Windows high contrast, no `overflow-hidden`) is in `DashboardCard`; its text is already the page's size (`src/index.css`). A card's table needs the room for its columns, because `ResponsiveTable` chooses table or cards from the window and not from its card; a card that does not fit fails `outsideItsCard` in `e2e/display.spec.ts`, which runs at the zoom widths and at 1440px and 1920px wide.
- A printout leaves out the app shell, the header and the sidebar (`print:hidden`, in `src/components/site-header.tsx` and `src/components/ui/sidebar.tsx`), and with them the app title, so a printable page writes its own title, as How to sign in does.
- A Report goes inside `ReportFrame` (`src/components/report-frame.tsx`), which writes the title block and sets the page title and the page number's margin (in `src/index.css`; README [Reports](README.md#reports)). Don't write a Report's own title or `@page` rules. A Report's page also holds its heading (with the "?" whose sheet says what it holds) and its form, which are for the screen (`print:hidden`, in `ReportGate`): the page's h1 is that heading on screen and the frame's title on paper, so a printout is the Report alone and a page never has two h1. "Print or save as PDF" is in the form's row of buttons beside "Show Report", once a Report shows, and above the Report for a Member, who has no form (`useReportPrint`, `ReportGate`).
- A Report's tables are `ResponsiveTable` with `className="print:text-[12pt]"` and `printHeading={useReportIdentity()(account)}`, so every printed page says what it is in every browser; nothing in a Report is under 12pt in print.
- A Report that lists rows reads them a page at a time from `/api/reports/…` (ADR 0004), through `loadListing` in `src/lib/report-transactions.ts` and its cap (or, for a Report whose sections are not Accounts, through `readUpToCap`, the loop under it, with a cap of its own), and says what it did not read (never "nothing" for an Account it stopped before).
- A new Report adds its print layout (page count, repeated headings, type size) to `e2e/reports.spec.ts` (or a spec of its own, as `e2e/report-balances.spec.ts` is), through the shared checks in `e2e/report-helpers.ts` rather than a copy of them, and its page to the zoom test. A Report has a page of its own, with a row in the Admin's sidebar, which come from its entry in `REPORTS` (`src/lib/reports.ts`): its name and its page's words are written once there, and the page's route declares `nav: reportNav(REPORTS.x)`. It is also one of the six in `REPORT_IDS` and `SHAPES` (`worker/kept-reports.ts`), which say what choices it has, so that the Admin's showing it can be kept and a Member can open it once it is (a test fails if a route under `/api/reports` is not listed). Its form is built from `ReportForm` (`src/components/report-form.tsx`), which shows the Report on the same page (the choice goes into the Report's address) and reads it again when the Report that is open is asked for again, so each form names itself and has its own field ids.
- A Report's page is a `ReportGate` (`src/components/report-gate.tsx`) around a component that reads its data and puts `reportWaiting` before its `ReportFrame`, so every Report asks for its Account and dates, loads, and fails in the same words. A Report's query string starts from `reportRange` (or `reportRangeOfAll`, with the Account optional, when one request can cover every Account, or `reportDates` alone when it takes no Account, as Budget vs actual's does) and ends with `datesInOrder` (`worker/report-query.ts`). The Loans Report may begin at the first Transaction, so its query is `reportDates` with `from` optional and a `reportId` for its Category, and ends with its own `startIsNotAfterEnd` (`worker/report-loans.ts`); `datesInOrder` stays strict for a Report that must have both dates. What a Report says when what it was asked for cannot be shown (an Account or Loans Category that is not there, dates that cannot make a Report) is `NeedsChange` (`src/components/report-gate.tsx`), which sends the Admin to the form and a Member, who has none, to the list of Reports; never write "use the form" for a reader who may be a Member.
- A Report that shows balances takes them from balance history (`HISTORY_CTES` in `worker/balances.ts`) and picks rows out of it in SQL, never a second calculation, with a Seam 1 test that holds its numbers to `/api/balances/:id/history`. A chart of balances does the same: net worth (`worker/net-worth.ts`) runs the balances Report's `REPORT_HISTORY` for each Account, carries quiet months with the Report's own `carryForward` (`worker/month-balances.ts`) and only adds them.
- A chart (`src/components/charts`) is built from `ChartContainer` and `ChartFigure` (`src/components/ui/chart.tsx`) and takes every number from the Worker as it arrives, adding up none. It sits in a `ChartFigure` whose sentence says what it shows, with its figures beside it as a `ResponsiveTable`; draws with `isAnimationActive={false}` and `accessibilityLayer={false}`; colours itself only with a chart token that `scripts/theme-contrast.test.mjs` pins at 3:1 against the page, a card and the muted fill in both themes (`--chart-2` today; the stock `--chart-1` fails in dark, so add a token to that test before using it); and sizes its text and rows in rem. A chart is loaded where it is shown (`LazyNetWorthChart` and `LazySpendingChart`, `src/components/charts/lazy-charts.tsx`): the chart library is large and no other page needs it, and an `ErrorBoundary` around the `Suspense` says so, and leaves the rest of the page, when its chunk cannot be loaded (a tab left open across a deploy). A chart on a Report is drawn from the Report's own answer, asks for nothing more, and is `print:hidden`, because the Report's tables are what is printed. A new chart is a card (above) on a page of its own, or a part of a Report, and adds a long-content case to the zoom tests in `e2e/display.spec.ts` and an axe check (the Net worth page's and the Spending by Category Report's are in `e2e/shell.spec.ts`; its colours are in the sweep in `e2e/contrast.spec.ts`, which draws both charts).
- Spending by Category, for the Report and the chart drawn from it, comes from `readSpendingByCategory` (`worker/spending-by-category.ts`): its Categories, names, order and total are written once, and a caller restates none of them. Show a Spending figure with `Spent` (`src/components/spent.tsx`), so "$15.00 back" reads the same everywhere. A Report of it has a Seam 1 test that holds its rows and total to `/api/charts/spending`.
- Budget vs actual, for one month or many, comes from `budgetVsActual` and `budgetInMonth` (`worker/budget-rules.ts`) over `buildSpending`'s rows; the Budget vs actual Report (`worker/report-budget.ts`) calls them for each month and a test holds each month to `/api/budgets/vs-actual`. A second rule for which Budget a month has, or a second total of what a month spent, is a bug. A month's rows and columns are `budgetRows` (`src/lib/budgets.ts`) and `budgetColumns` (`src/components/budget-columns.tsx`) on the Summary and in the Report, so "Under Budget" and "$15.00 back" read the same in both. Months added together leave out a month that has not ended (the month it is now has part of its spending against the whole of its Budget), and the Report says which it covers (`together`). A Report of Spending puts `NOT_COUNTED`, and one of Spending and Income together `NOT_COUNTED_AS_SPENDING_OR_INCOME` (both in `src/lib/budgets.ts`), in the heading of each table on paper (`useReportIdentity()(accounts, …)`), so every printed page says what is left out.
- The Transactions of a Loans Category, for a Report or anything else that lists them, come from `buildLoanPage` (`worker/report-loans.ts`). What a loan is comes only from `isLoan` (`worker/spending.ts`) over `effectiveCategory().shown`, and a Category is a Loans Category only by `isLoansKind` (`worker/category-kinds.ts`, `src/lib/category-kinds.ts` for the pages); a query never reads `transfer_of` or `rule_transfer` for it. The Loans Report has a test that what it lists is what `buildSpending` sets aside as Loans. A loan's balance is owed with the sign turned (`owedOf`, `src/lib/report-loans.ts`) and worded there ("Alice owes $300.00 to the Accounts", "Alice is owed $300.00"), never with "we" ([GLOSSARY](GLOSSARY.md), Loans Report).
- A request that adds up a number for every Account takes one D1 query for each, so it states how many Accounts it reads (under the 50 queries of ADR 0004) and refuses more rather than total only some of them.
- A Report of months (`worker/report-income-vs-spending.ts`) uses `buildMonthlySpending` and `rollUpMonthly` (`worker/spending.ts`): `buildSpending`'s one statement grouped by month and kind, so D1 hands the Worker a few rows a month and not one for every Category, and itself only fills the months with nothing in them and subtracts. A new total over months groups the same statement (`spendingStatement`) and does not write its own SELECT. Whether there was "no income or spending" is `counted` (Transactions), not figures that net out to nothing.
- Show state with a border or outline as well as a box-shadow or fill: Windows high contrast removes the latter. Focus is a `focus-visible:outline-*`, and never beside `outline-none`, which sets the outline style to none.
