# Akahu's balance is a bank balance, recorded after each finished Sync

After a Sync of an Account finishes, Fernledger records the balance Akahu reports for it as a bank balance (`balance_checks`, source `sync`) and runs the Balance Check on it as it does for a file's balance (ADR 0011). The pure rules are `syncBalance` in `worker/balance-rules.ts`; Sync does the recording (`worker/sync.ts`).

A file's balance is a figure as at a date, and its Transactions are in the file. Akahu's `balance.current` is a figure as at an instant (`refreshed.balance`), and a finished Sync holds the Transactions Akahu had read by `refreshed.transactions`. The two agree only if Akahu read them at the same moment, so:

- **Recorded only when the Sync finished and both refreshed times are the same moment.** If they differ, either side could hold a Transaction the other lacks, and the Balance Check would report that gap as a missing or duplicated Transaction. A Sync that did not finish has not read the whole window. A balance Akahu did not send, or in a currency other than NZD, is not recorded. Nothing is guessed: no balance is better than one that cannot be compared honestly, and the Account's next Sync tries again. The cost is that an Account whose two times never match never gets a balance from Akahu; the Sync log says `sync.balance.refreshed-apart`.
- **Dated the NZ day Akahu read the bank,** not the day of the Sync. A stale connection, or a second Sync of the same reading, records the same balance on the same date and adds no row. Transactions dated that day and saved by the Sync count in it (`through_transaction_id`), as for a file.
- **The Cutover Date does not uncount it.** A file's balance dated on or after the Cutover Date is set aside because those days belong to Sync (ADR 0003), and the Sync balance is what covers them. An Akahu balance is after the Cutover Date by nature, so the rule is not applied to it. It is counted: it anchors the Account's balance and history, and the Summary's As of date moves to the day Akahu read the bank. A file's balance already set aside stays set aside.
- **One a day, kept 60 days.** The date is the key, so a second reading on the same NZ day replaces the first. Each balance is compared with the one before it, so a daily one dates a difference to the day it appeared. Older than 60 days are dropped at the end of a Sync, except an Account's newest, which may be its only anchor if its link stops syncing. Dropping never hides a difference: the next balance is compared with the one before the dropped one, so the difference shows with an earlier "since" date. Without it the Balance Check, which reads every balance of an Account to check them, would cost more reads each year.
- **A failed check does not fail the Sync.** The Account's Transactions and mark are committed before the check; if it fails it is logged and runs again at the next Sync.

## Consequences

- An Account now costs 11 D1 queries at most, not 8 (the balance statement joins the batch, and the check is one read and one write), and one query at the end drops old balances. A run takes four linked Accounts, not five; a fifth waits for the next run, which takes the least recently synced first (ADR 0004).
- "Bank balance" in the glossary and README means the latest of either source. `balance_checks.source` says which.
- Two overlapping Syncs (ADR 0013) record the same balance on the same date and run the same check twice: the result is the same.
