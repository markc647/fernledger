# Runs on the Cloudflare Workers Free plan

The app must run within the Workers Free plan, so anyone can self-host it at no cost. That rules out anything that needs Workers Paid, such as Containers or long CPU-bound requests.

## Consequences

- Each request and cron run gets 10 ms of CPU. Waiting on D1 or `fetch` doesn't count, but parsing and looping in the Worker does. Heavy work is split up: a large CSV Import is parsed in the browser and sent in chunks of about 500 rows, and Rules re-run as SQL, not in JS loops. A CSV export is written by D1 in chunks of at most 500 Transactions and 256 KB, each one finished string, so the Worker only passes text along, and it stops at 5,000 Transactions or about 0.75 MB (`worker/transaction-export.ts`): reading and formatting 50,000 rows in JS measured about 100 ms in Node, and a 10,000-row export's own steps 4 to 6 ms in a local workerd on a busy machine, which leaves too little of 10 ms. These are estimates, since CPU can't be seen from a test; lower the limits if CPU errors (1102) show.
- A single invocation is limited to 50 subrequests and 50 D1 queries. Writes are batched, and Sync pages are written with one batch per page.
- D1 Free allows 100k rows written per day. A full Import or a Rule re-run over all history must stay well under that. An imported row costs 4 of them (the row and its three indexes, pinned in `worker/imports.test.ts`), so a full Import of 10,000 rows is 40,000, and removing a row is taken to cost the same, so replacing an Account's imported history is 8 a row (`worker/import-rows.ts` has the rest). The re-run keeps to it in code (`worker/rule-rerun.ts`): it adds up the rows D1 reports for each of its steps, per UTC day (D1's allowance resets at 00:00 UTC, about midday in New Zealand), and pauses before a step that would take it past 2.5 million rows read or 40,000 written in a day, so the Members, an Import and the backup keep the rest. It sizes each step to the number of Rules (about 25,000 reads), writes only the Transactions whose result changes, and carries on by itself after the day changes.
- D1 Free allows 5 million rows read per day, and bills the rows a query reads, not the rows it returns. A query with no usable index reads the whole table, and a `COUNT` reads every row it counts. So a list pages off an index and stops after one page, and a total is counted once per search, not per page; a caller that shows no total (the Summary) doesn't count. A text search, or a sort by any column but date, reads every Transaction the other filters keep, and a sort reads each about three times (the scan, an Account lookup and the sort), five for a paired Transfer (its matching Transaction and that one's Account). At 100,000 Transactions that is about 300,000 rows a page, or 15 pages a day; at 10,000, about 150. A CSV export pages by date and ID, not OFFSET, so it reads each Transaction it writes about seven times (its place in the date index, the row, its Account, one for each Category source that supplies its Category, and three for the sort that sizes a chunk): 35,000 reads for a full 5,000-row file, or about 140 of them a day. A Category filter with few Transactions in it (up to about 1,000 in its Override and Rule indexes) starts from those indexes, as the list does, and reads only them, about a dozen to seventeen reads for each Transaction in the Category rather than about three for every Transaction there is. Tests pin the rows read (`worker/transaction-search.test.ts`, `worker/transaction-export.test.ts`), so a change that makes a request read more fails.
- The Admin can see how much of the day the account has used, with the optional D1 usage bar (README [What it does](../../README.md#what-it-does); ADR 0010).
- The balances Report (`worker/report-balances.ts`) is one request for each Account. Balance history works out every balance from the bank's balance and all of the Account's Transactions, so no dates can be skipped: it reads each Transaction about five times, and the Report about six (the history, and its rows again for each of the four kinds of row it picks out), however narrow its dates. But it returns a row a month, not the history's row a day, so the Worker does no loop over days. At 10,000 Transactions that is about 62,000 reads a Report, or about 80 a day for that Account. `worker/report-balances.test.ts` pins the reads.
- Spending (`worker/spending.ts`, [ADR 0012](0012-spending-and-category-kinds.md)) is totalled in SQL over the date index, so only the dates asked for are read, and it reads each Transaction in them three times (its place in the date index, the row, and its Override's Category), or four when a Rule also names a Category: a month of 500 Transactions is 1,500 to 2,000 rows, and a year for a Report is twelve times that. The Summary's Budget vs actual reads one month on every visit, and it is all that landing on the Summary or the Dashboard reads of this (neither has a chart: the charts are on pages of their own, below), so at 500 Transactions a month about 2,500 visits would use a day's 5 million. The Budgets page reads every Budget change, at most 600 (`MAX_BUDGET_CHANGES`), and looking up one Category's Budget in a month is a single seek. Tests pin the rows read (`worker/spending.test.ts`, `worker/budgets.test.ts`).
- The Income vs spending by month Report (`worker/report-income-vs-spending.ts`) runs `buildMonthlySpending`, which is `buildSpending`'s statement (spending.ts builds both from one, so what they leave out and how they read a Transaction is written once) grouped by NZ month and kind, and by whether there is a Category, instead of by Category. Whatever the number of Accounts it is one D1 query, plus one to check an Account it is asked about (two for one Account, one for all). It reads each Transaction in the dates as many times as the Spending by Category Report does, three, or four when a Rule also names a Category, so a Report of the most it covers reads as much (about 400,000 rows at 100,000 Transactions over the whole history, and about 12 of them use a day's 5 million); `worker/spending.test.ts` holds the two statements to the same rows read (it was 1,600 against 1,601 for 400 Transactions). **It covers at most 120 months, 10 years (`MAX_INCOME_MONTHS`; a request beyond is refused with a 400 naming `to`, and the form and the address say so first).** **What changed the Worker's CPU is that D1 does the grouping, so it hands the Worker at most four rows a month** (Spending in a Category, Uncategorised Spending, Income, and Loans, which the Worker leaves out): 480 at 120 months however many Categories there are, where `buildSpending` hands it a row for every Category with something in each month (about 12,000 at 100 Categories and 72,000 at 600). `worker/report-income-vs-spending.test.ts` pins the one query, the 480 rows returned and the rows read for a Report of 120 months, and that a year of 480 Transactions in one Category returns 12 rows. The Worker then writes a row for each month the dates touch, at most 120. The grouping is SQLite's work inside D1, which is not the Worker's CPU but is not free, and it is not measured here: the statement still reads each Transaction as above. CPU can't be seen from a test in workerd, but the Worker's side was timed in Node at the cap, 120 months, by `scripts/bench-income-vs-spending.mjs` (run by hand, not part of `npm run check`), in a fresh process for each size and function and nine processes for each figure, on an Intel Core i5-1235U (12 threads, Windows, Node 24.20). It is not a measurement of the free plan's 10 ms, and it leaves out what it costs D1 to hand the rows to the Worker. For the Report's whole function (the roll-up, the months and the JSON), the **first call in a process** now takes about 1 to 2 ms at 30, 100 and 600 Categories, and later calls take 0.1 to 0.3 ms at every size, because the rows are the same few hundred whatever the Categories. Before, when D1 handed over a row for every Category-month, the same function took 1.8 to 3.3 ms, 5.8 to 8.4 ms and 11 to 16 ms the first time (about 6 to 8 ms at a household's 100 Categories, and 9 to 15 ms in a run on a busy machine, which is near the 10 ms limit), and 0.3 to 0.5, 0.4 to 0.7 and 1.8 to 3.0 ms after; and `rollUp` over those rows, which is what the Report first called, took 1.7 to 3.4, 4.2 to 5.1 and 18 to 22 ms the first time and 0.2 to 0.3, 0.9 and 4.4 to 6.1 ms after. The before figures came from the per-Category path that was replaced, which the committed script can't regenerate (its `rollUp` row still times that roll-up). Decoding the rows D1 returns is the Worker's CPU too, and is 480 rows now and was tens of thousands then; that is not in these figures either way. The cap stays at 120 (it was chosen, not derived from these figures), and it bounds the months. Lowering `MAX_INCOME_MONTHS` is the lever if CPU errors (1102) show.
- **Landing on the Summary or the Dashboard must not read more than it did.** The two pages are the same three cards (Balances, Budget vs actual, and the newest Transactions), and they read what those need and no chart: the balances (which also say whether Akahu synced each Account in the last 24 hours, from a column of a row the query already reads), the Balance Checks (the Balances table uses both answers, and asks for each once), this month's Budget vs actual and the newest few Transactions with no count. The one request that is new is `GET /api/features`, which says whether Akahu Sync is set up for the Sync column: it looks at the Worker's secrets and reads no D1 row, so the landing page's D1 reads are what they were. The charts read every Transaction they cover, so they were moved off the landing page to where they wait: net worth to the Net worth page, and spending by Category to the Spending by Category Report, whose chart is drawn from the Report's own answer. `e2e/dashboard.spec.ts` holds the landing page to the requests it makes and to none for a chart or a Report.
- Net worth (`worker/charts.ts` and `worker/net-worth.ts`) is one request, and the Spending by Category Report's chart is none. Net worth adds up balance history, which [README](../../README.md#how-it-works) explains: it runs the balances Report's month-end query for each Account, so it reads every Transaction about six times and uses 1 + N of the 50 D1 queries for N Accounts, and it refuses more than 49 Accounts, with a flag the page words, instead of totalling only some. **A range does not cut the reads.** Balance history is worked out from the bank's balance and every Transaction of the Account, so `range=24-months` reads exactly what `range=all` does and only returns fewer months (`worker/charts.test.ts` pins both). The cost of one request is therefore about 60,000 rows at 10,000 Transactions (about 80 requests to use a day's 5 million) and about 600,000 at 100,000 (about 8). So net worth is drawn only when it is asked for: the Net worth page asks when the reader presses "Show net worth", and the range is chosen beside the button, before or after, so choosing first costs one read and not two. Opening the page reads nothing, and each time net worth is drawn it costs about 6 reads for each Transaction. The browser keeps the answer for five minutes, does not ask again when the window is refocused, retries a failure once, and asks sooner only after an Import or a change of Cutover Date. Only a history worked out from the Transactions after a date, rather than from all of them, would read less; that would be a second calculation of balances, which this ticket does not write. Spending by Category (`worker/spending-by-category.ts`) is one query whatever the dates: spending.ts's totals with each Category's name, read as above (three or four reads for each Transaction in the dates). The Spending by Category Report (`worker/report-spending.ts`) calls it, plus one more D1 query to check the Account it is asked about: one query for all Accounts, two for one. The bars on the Report's page are drawn from that answer in the browser, so the chart adds no request and no read to the Report (`e2e/report-spending.spec.ts` holds the page to the one request). The Report has no limit on its dates, so a Report of the whole history reads about 400,000 rows at 100,000 Transactions, and about 12 of them use a day's 5 million. (`GET /api/charts/spending`, which the Summary's chart used to ask with a named period or two dates, is asked for by no page now; it is still in the Worker, and the Reports' tests compare their figures with its answer.) D1 hands back a row for each month and Category, which the Worker adds together (a few hundred rows for a year, a few thousand for a whole history). CPU can't be seen from a test, so what that costs is not measured; limit the dates a Report takes if CPU errors (1102) show. `worker/report-spending.test.ts` pins the queries and the rows read.
- The Budget vs actual Report (`worker/report-budget.ts`) is one request for all Accounts, because a Budget is for all of them together, and one D1 batch of three statements whatever the months: the Spending Categories in use (about two rows read for each, three for one with a Budget), every Budget change (at most 600, `MAX_BUDGET_CHANGES`), and the spending of the whole months the dates touch. The spending reads each Transaction in those months three times, or four when a Rule also names a Category, as above, so a year of 500 Transactions a month is 18,000 to 24,000 rows and a Report of the most it covers, 24 months, twice that; at 500 Transactions a month that is about 100 Reports to use a day's 5 million. **The 24-month cap (`MAX_REPORT_MONTHS`, which a request beyond is refused with a 400 naming `to`) bounds the months, not the Categories.** A Category has a row in a month only while it has a Budget, and every Category with a Budget has at least one of the 600 changes, so a month has at most 600 rows and a Report at most 600 × 24 = 14,400, about 1.7 MB of JSON; `worker/report-budget.test.ts` pins that worst case with 600 Categories over 24 months, in the same three statements and about three rows read for each Category. The Worker applies the Budgets with a loop over every Spending Category in use and every month (`budgetInMonth`, which looks through that Category's own changes), which has no limit of its own beyond the number of Categories. CPU can't be seen from a test in workerd, but the loop and the response were timed in Node (a review's measurement, not a measurement of the free plan's 10 ms): the worst case, 600 Categories with a Budget over 24 months, took about 17 ms warm and about 56 ms cold, plus about 7 ms to write the JSON, so **the worst case can exceed the 10 ms limit**; 100 Categories took about 3.5 ms and 30 about 1 ms. The cap on months stays at 24 and does not shrink as Categories with a Budget grow: a household's few dozen Categories are well within the limit, and 600 Categories with a Budget is not a household, so a smaller cap for that case was not built. Lower `MAX_REPORT_MONTHS` if CPU errors (1102) show.
- The Loans Report (`worker/report-loans.ts`) is one request for each page of each Loans Category. A request is two D1 queries (one to check that the Category is a Loans Category, one for the page), or three for the first page of a loan with a start date (the opening balance), which a one-Transaction probe, sent when the cap has been reached, is too. It finds the Category's Transactions through the indexes on `override_category` and `rule_category`, as a Category filter on the Transactions list does (`categoryCandidates`), so the household's other Transactions are not read. But it reads all of the loan's Transactions for every page, since they are put in date order after they are found: about 6.3 reads for each Transaction of the loan (the two indexes' entries, the row, its place in the sort, its Account, and its Override's and Rule's Categories), 5 when no Rule names a Category. The opening balance is a statement of its own and reads the loan again: 3 reads for each Transaction of the loan, and 1.3 more (its Override's and Rule's Categories) for each one before the start date, 4.3 at the most. That makes a loan's cost its size times its pages, so with the Transaction listing's 200 a page it would grow with the square of the loan (a loan of 10,000 Transactions would be 50 pages of about 63,000 reads, over 3 million, most of a day's 5 million). So the Loans Report has its own page of 1,000 (`LOANS_PAGE_SIZE`, the most a request may ask for) and its own cap of 5,000 Transactions across the loans (`LOANS_ROW_CAP`), and a family's loan, which is tens or hundreds of Transactions, is one request: 300 Transactions cost about 1,900 reads. The worst Report within the cap is a loan of 5,000: five pages and the probe that finds out whether more were left out, each of about 31,500 reads, and the opening balance on top (up to 21,500), about 210,000 in all, or about 24 such Reports in a day's 5 million. A loan beyond the cap, which only a mistake makes, such as a Rule that sends every Transaction to a Loans Category, costs as much for each of its six requests as it holds, however few rows it returns: about 2 million reads for the Report at 50,000 Transactions and about 4 million at 100,000, a day's allowance. That is accepted: a count to refuse such a loan before reading it would itself read the whole loan, the Report says it stopped at the cap, and it costs only when a Member opens the Report. For CPU, a page of 1,000 rows (about 190 KB of JSON) takes about 1 to 2 ms in Node to slice and serialise (1.2 ms the first time; a review that timed the whole handler saw 3 to 4 ms), against 10 ms. CPU can't be seen from a test and Node is not workerd, so it is an estimate; lower the page size or the cap if CPU errors (1102) show. `worker/report-loans.test.ts` pins the queries, the rows read for one page, for the opening balance on its own and for all the pages of a loan, and the page size the Report page asks for.
- Clearing an imported history of more than 5,000 rows in steps (`POST /api/imports/clear-history`, `worker/imports.ts`) before it is replaced removes the oldest-dated 5,000 rows of the Account in each step. They are taken by searching the Account in the index `transactions_account_date` in its own order (date, then ID), and each walk of that search reads about a slice and sorts nothing: a step read 90,262 rows at 5,201 rows and 105,061 at 20,000, and the same with 20,000 or 100,000 rows of another Account in the table. Taken in ID order instead, SQLite sorts every row of the Account in each statement, and with the check below a step read 138,875 at 5,201 rows behind another Account's 100,000, and 420,056 at 20,000 rows alone (measured). Each step also checks that its slice is still the one it counted, once before and in each of its four statements (at most five walks of a slice, about 5,000 reads each), by finding the first row it leaves, the 5,001st. In ID order that check either sorts the Account's rows each time, or, forced to walk the table (`NOT INDEXED`), reads every other Account's rows below it too (105,001 a walk behind another Account's 100,000 rows, measured). Cleared in steps, a history of 100,001 rows took 20 steps and 2,656,184 rows read (measured), about half a day of the allowance; in ID order the same history took 10,656,344 with the walk and 18,851,425 with the sort (measured, one Account). `worker/cutover.test.ts` pins the plans and the reads.
- There are at most 5 cron triggers per account. We use 3: daily Sync, Sync retry, and weekly backup.
