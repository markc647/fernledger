# Runs on the Cloudflare Workers Free plan

The app must run within the Workers Free plan, so anyone can self-host it at no cost. That rules out anything that needs Workers Paid, such as Containers or long CPU-bound requests.

## Consequences

- Each request and cron run gets 10 ms of CPU. Waiting on D1 or `fetch` doesn't count, but parsing and looping in the Worker does. Heavy work is split up: a large CSV Import is parsed in the browser and sent in chunks of about 500 rows, and Rules re-run as SQL, not in JS loops. A CSV export is written by D1 in chunks of at most 500 Transactions and 256 KB, each one finished string, so the Worker only passes text along, and it stops at 5,000 Transactions or about 0.75 MB (`worker/transaction-export.ts`): reading and formatting 50,000 rows in JS measured about 100 ms in Node, and a 10,000-row export's own steps 4 to 6 ms in a local workerd on a busy machine, which leaves too little of 10 ms. These are estimates, since CPU can't be seen from a test; lower the limits if CPU errors (1102) show.
- A single invocation is limited to 50 subrequests and 50 D1 queries. Writes are batched, and Sync pages are written with one batch per page.
- D1 Free allows 100k rows written per day. A full Import or a Rule re-run over all history must stay well under that. An imported row costs 4 of them (the row and its three indexes, pinned in `worker/imports.test.ts`), so a full Import of 10,000 rows is 40,000, and removing a row is taken to cost the same, so replacing an Account's imported history is 8 a row (`worker/import-rows.ts` has the rest). The re-run keeps to it in code (`worker/rule-rerun.ts`): it adds up the rows D1 reports for each of its steps, per UTC day (D1's allowance resets at 00:00 UTC, about midday in New Zealand), and pauses before a step that would take it past 2.5 million rows read or 40,000 written in a day, so the Members, an Import and the backup keep the rest. It sizes each step to the number of Rules (about 25,000 reads), writes only the Transactions whose result changes, and carries on by itself after the day changes.
- D1 Free allows 5 million rows read per day, and bills the rows a query reads, not the rows it returns. A query with no usable index reads the whole table, and a `COUNT` reads every row it counts. So a list pages off an index and stops after one page, and a total is counted once per search, not per page; a caller that shows no total (the Summary) doesn't count. A text search, or a sort by any column but date, reads every Transaction the other filters keep, and a sort reads each about three times (the scan, an Account lookup and the sort), five for a paired Transfer (its matching Transaction and that one's Account). At 100,000 Transactions that is about 300,000 rows a page, or 15 pages a day; at 10,000, about 150. A CSV export pages by date and ID, not OFFSET, so it reads each Transaction it writes about seven times (its place in the date index, the row, its Account, one for each Category source that supplies its Category, and three for the sort that sizes a chunk): 35,000 reads for a full 5,000-row file, or about 140 of them a day. Tests pin the rows read (`worker/transaction-search.test.ts`, `worker/transaction-export.test.ts`), so a change that makes a request read more fails.
- The balances Report (`worker/report-balances.ts`) is one request for each Account. Balance history works out every balance from the bank's balance and all of the Account's Transactions, so no dates can be skipped: it reads each Transaction about five times, and the Report about six (the history, and its rows again for each of the four kinds of row it picks out), however narrow its dates. But it returns a row a month, not the history's row a day, so the Worker does no loop over days. At 10,000 Transactions that is about 62,000 reads a Report, or about 80 a day for that Account. `worker/report-balances.test.ts` pins the reads.
- Spending (`worker/spending.ts`, [ADR 0012](0012-spending-and-category-kinds.md)) is totalled in SQL over the date index, so only the dates asked for are read, and it reads each Transaction in them three times (its place in the date index, the row, and its Override's Category), or four when a Rule also names a Category: a month of 500 Transactions is 1,500 to 2,000 rows, and a year for a Report is twelve times that. The Summary's Budget vs actual reads one month on every visit, so at 500 Transactions a month about 2,500 visits would use a day's 5 million. The Budgets page reads every Budget change, at most 600 (`MAX_BUDGET_CHANGES`), and looking up one Category's Budget in a month is a single seek. Tests pin the rows read (`worker/spending.test.ts`, `worker/budgets.test.ts`).
- The charts (the Charts page and the Dashboard, `worker/charts.ts`) are two requests. Net worth (`worker/net-worth.ts`) adds up balance history, which [README](../../README.md#how-it-works) explains: it runs the balances Report's month-end query for each Account, so it reads every Transaction about six times and uses 1 + N of the 50 D1 queries for N Accounts, and it refuses more than 49 Accounts, with a flag the page words, instead of totalling only some. **A range does not cut the reads.** Balance history is worked out from the bank's balance and every Transaction of the Account, so `range=24-months` reads exactly what `range=all` does and only returns fewer months (`worker/charts.test.ts` pins both). The cost of one request is therefore about 60,000 rows at 10,000 Transactions (about 80 requests to use a day's 5 million) and about 600,000 at 100,000 (about 8). So net worth is drawn only when it is asked for: the Charts page asks when it opens, and the Dashboard asks when the Admin presses "Show net worth". Landing on the Dashboard costs only the Summary's widgets and the spending chart, and each time net worth is drawn it costs about 6 reads for each Transaction. The browser keeps the answer for five minutes, does not ask again when the window is refocused, retries a failure once, and asks sooner only after an Import or a change of Cutover Date. Only a history worked out from the Transactions after a date, rather than from all of them, would read less; that would be a second calculation of balances, which this ticket does not write. Spending by Category (`worker/spending-by-category.ts`) is one query whatever the dates: spending.ts's totals with each Category's name, read as above (three or four reads for each Transaction in the dates). The named periods are at most 12 months; two dates can span the whole history, which at 100,000 Transactions is about 400,000 rows. The Spending by Category Report (`worker/report-spending.ts`) calls the same function, so it reads the same, plus one more D1 query to check the Account it is asked about: one query for all Accounts, two for one. It has no limit on its dates, so a Report of the whole history reads about 400,000 rows at 100,000 Transactions, and about 12 of them use a day's 5 million. D1 hands back a row for each month and Category, which the Worker adds together (a few hundred rows for a year, a few thousand for a whole history). CPU can't be seen from a test, so what that costs is not measured; lower the range the page offers if CPU errors (1102) show. `worker/report-spending.test.ts` pins the queries and the rows read.
- There are at most 5 cron triggers per account. We use 3: daily Sync, Sync retry, and weekly backup.
