# An Account number is the Account's key, which is the bank's number when the bank prints one

`accounts.account_number` is the Account's stable key: the one value an Import matches a file against, the one `transactions.account_id` is resolved through on insert, and the one a Report prints beside the Account's name. For every Account Fernledger has held so far it is the number the bank prints, `BB-bbbb-AAAAAAA-SS`. A credit card has no such number, so for an Account whose bank prints none, **Fernledger generates the key** (`card-0001`), and the column keeps its job and its `NOT NULL UNIQUE` constraint.

A card number is not a key. A card is reissued on fraud or expiry, and one real Kiwibank export held three card numbers for a single account over two years, so an Account keyed on a card number would split in two at the next reissue. The card's last four digits belong where they say which card was used: `transactions.bank_card_suffix`, per Transaction, where a reissue shows up in the history rather than breaking it.

- **The key is Fernledger's, not the bank's, and the Admin never types it.** The Admin creates such an Account by name ("Add a Credit Card Account" on the Accounts screen) and names it thereafter; the key is allocated by the Worker. `accountKey` (`worker/account-fields.ts`) is what crosses the API where a stored key travels: the bank's shape, or `card-` and at least four digits. A CSV adapter still produces the bank's own shape for a bank that prints a number; an Import that names a generated key for an Account that is not there is refused, because only the Worker hands those out.
- **A generated key is never shown where a bank's number is expected.** The Accounts table says "None from the bank" in its Account number column, and a Report heading and the Import preview give the Account's name alone. The Account's name is what identifies it to a Member; the key is plumbing, and showing it as a number would be a lie about what the bank issued.
- **An Import whose file carries no account number asks which Account it is for.** Nothing is matched, because there is nothing to match on, and the screen offers only Accounts whose key Fernledger generated: a file with no account number is a card export, and offering a bank-numbered Account would invite putting a card's Transactions into a cheque account.
- **A card Account has no Balance Check from CSV.** Kiwibank's card export prints no balance, so `BankCsvResult` no longer requires a `ledgerBalance` and the Worker's chunk request takes it as optional. Nothing is inferred from the Transactions to stand in for a bank balance: the whole point of the check is to compare what the bank says with what the Transactions add up to, so one side of it cannot be made up. Through Akahu such an Account is checked like any other, from Akahu's own balance (ADR 0014).
- **No migration.** The column already accepts any text, and the bank's shape was only ever enforced in app code, so this ticket writes no SQL. Accounts already held keep the bank's number, and nothing is re-matched.

## What was rejected, so it is not re-litigated

- **Identity becomes the internal `id`, with the number optional.** Honest, and it would handle anything a bank does not number, but it moves about twenty internal scope keys from `accountNumber` to `accountId` and needs an existing `NOT NULL` column made nullable, which SQLite does by rebuilding the table — the opposite of the add-only rule in [ADR 0009](0009-expand-contract-migrations.md), with live data in it. Nothing here blocks doing it later if something else demands it.
- **Credit cards only through Akahu.** No code, but the card's CSV history is lost (about six months in the sample), and it contradicts [ADR 0008](0008-akahu-optional.md): every feature must work without Akahu.

## Consequences

- The key's shape carries the one thing Fernledger knows about such an Account: that the bank prints no number for it. There is no account-type column, and `card-` is not one; an Account kind, if it is ever wanted, is a ticket of its own.
- Keys are allocated as the highest card key held plus one, worked out inside the insert (`ADD_CARD_ACCOUNT`, `worker/accounts.ts`). One statement reads and writes, so two requests cannot read the same highest number and both write it, and the `UNIQUE` constraint is left with nothing to decide. A key is never reused: removing an Account is not something Fernledger does, and if it ever is, the highest key held is still what the next one follows.
- A card Account still needs a Cutover Date before Sync will touch it (`windowStart`, `worker/sync.ts`), and gets one the way any Account does: the Import's offer, or Settings.
- A file that states no balance is now accepted for any Account, not only a card one, so an adapter that silently dropped a balance would skip the Balance Check rather than be refused. Where a bank does state one, its adapter is what insists on it: ASB's refuses a file whose Ledger Balance header is missing, and Kiwibank's takes the last row's. That is the right place for it — the Worker cannot know which banks print a balance.
- Account names are not unique, here or anywhere else in Fernledger, and the Import's "Which Account is this file for?" lists them by name, which is the one place the key is deliberately hidden. Two cards named the same are told apart only by their order in that list, and renaming one is the remedy.
- A bank that prints no number for an account that is not a credit card has no form of its own yet. The key's shape would want widening, or a second prefix, and that is the point to revisit whether identity should move to `id` after all.
